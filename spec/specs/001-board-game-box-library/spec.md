# Feature Specification: Board Game Box Library

**Feature Branch**: `001-board-game-box-library`

**Created**: 2026-08-11

**Status**: Draft

**Input**: User description: "Build a library that will help create boxes with special emphasis on board game boxes. Handle multiple different types of boxes, from hinged boxes to sliding lid boxes. Allow the indents inside the box to be laid out either automatically or at specific locations. Make sure the pieces have finger cut outs and other elements to make it easy to remove the pieces from the boxes and setup a 3d box shape making sure all of the sub boxes can fit inside the overall game box."

## Clarifications

### Session 2026-08-11

- Q: How is unused space distributed among expandable sub-boxes? → A: Fill-to-fit: boxes expand only to fill the row/column they share, aligning and matching sizes of other boxes in the same row/column. Leftover space goes to spacer boxes unless the gap is below the auto-fill threshold (default 10mm), in which case the adjacent box absorbs it.
- Q: What is the gap-to-expand threshold? → A: 10mm default; gaps smaller than this are absorbed by the adjacent expandable box instead of creating a spacer.
- Q: Spacer boxes: solid blocks or hollow trays? → A: Hollow trays (walls + floor matching the gap's footprint and height), constructed like any regular box for material efficiency.
- Q: Do boxes expand in both dimensions or one axis only? → A: Both dimensions expand. Boxes in the same row share a common length so every box in one row has the same length, making them easier to place and remove.
- Q: How are row widths determined when sub-boxes occupy multiple rows? → A: Variable width per row, sized to fit the widest box in that row -- rows are not forced to equal widths.
- Q: Multi-color 3MF: one file per box or per material? → A: One 3MF per box body and one per lid (separate files), each containing all colors/materials in a single 3MF.
- Q: Where do spacer trays go in 3MF exports? → A: Each spacer tray gets its own independent 3MF file.
- Q: How is "model differs" determined for content-based caching? → A: 3D-Hausdorff-Distance-Calculator comparing exported mesh geometry -- file is only rewritten if the geometric distance exceeds a tolerance.
- Q: Single-color vs multi-color export: toggle or always both? → A: Always generate both a multi-color 3MF and a single-color 3MF for every box body and every lid.
- Q: How do the three label layout modes (framed, frameless, diagonal) differ? → A: Diagonal is a text orientation (corner-to-corner of the lid, 45° only for square boxes), available in both framed and frameless modes. Framed mode adds a rectangular frame with diagonal hatching/webbing behind the text for bed adhesion plus a small outer border.
- Q: Lid pattern "spaces" for filament saving: holes, recesses, or lattice? → A: Through-holes cut completely through the lid at pattern lines -- maximum filament savings.
- Q: How many accent colors for lid decorations? → A: Three independently settable colors: one for label text, one for the frame (top layer), one for the pattern top layer. Patterns support multiple colors.
- Q: How does label auto-sizing determine dimensions? → A: Label fills available lid area minus a configurable border margin. If the computed text size is below a minimum (default 4mm, settable), the label is skipped entirely rather than printed illegibly.
- Q: How are box minimum dimensions computed from compartments? → A: `size` is auto-computed from compartment dimensions if not explicitly set. If `size` IS set, it is used as-is and compartments must fit within. Box expansion happens during the Project packing phase where sub-boxes are fitted into the main game box.
- Q: Should the packing layout PDF show a 2D top-down or 3D angle view? → A: 3D angle view with packing steps, showing how interior hidden boxes stack into the game box. Visualizes the packing order and interior box arrangement.
- Q: Is the PDF generated automatically or on-demand? → A: Automatic with every `project.export()`, but cached — only regenerates if the box layout or library version has changed since the last export.

## User Scenarios & Testing

### User Story 1 - Create a Basic Box with Interior Compartments (Priority: P1)

A board game designer wants to create a box to store game pieces. They specify the outer dimensions, wall thickness, and describe what compartments they need (e.g., "one large well for cards, two small wells for tokens"). The library generates a 3D-printable box with compartments laid out to fit the interior.

**Why this priority**: This is the core value proposition -- turning a description of storage needs into a printable box. Without compartments, there is no board game storage solution.

**Independent Test**: Can be fully tested by creating a box with 3 compartments of specified sizes, verifying they all fit within the box interior without overlapping, and exporting a printable 3D model.

**Acceptance Scenarios**:

1. **Given** a box outer size of 200x150x60mm and 3 compartments of specified dimensions, **When** the user generates the box, **Then** all compartments are placed within the interior, each separated by walls of the specified thickness, and no compartment overlaps another or breaches the box walls.
2. **Given** a box with compartments that exceed the available interior space, **When** the layout is computed, **Then** the library reports a clear error explaining which compartment or group cannot fit.
3. **Given** compartments with different depths (e.g., a shallow well for tokens and a deep well for cards), **When** the box is generated, **Then** each compartment carves to its specified depth and shared walls respect the deeper cavity.

### User Story 2 - Choose Among Different Box Lid Types (Priority: P1)

The designer needs different lid mechanisms for different use cases: a sliding lid for a box that sits on a shelf, a hinged lid for a box that opens like a book, a cap lid (friction-fit) for quick access, and a magnetic lid for premium feel. They select the box type and the library generates the correct geometry.

**Why this priority**: Lid type is the primary structural decision for a box. Without it, closures are not functional. Equal priority with compartments because both are needed for a complete usable box.

**Independent Test**: Each box type can be tested independently by generating a box and its matching lid, verifying the lid fits the box body, opens and closes as intended, and does not collide with interior contents.

**Acceptance Scenarios**:

1. **Given** the user selects a sliding lid box type with dimensions 100x80x40mm, **When** the box and lid are generated, **Then** the lid's two long edges carry an angled dovetail whose top face is the box interior (width − 2 × wall thickness) and whose bottom reaches half a wall width into each wall, sliding into matching dovetail grooves that leave half the wall behind them for support, so the lid can be removed only by sliding, never lifted out.
2. **Given** a sliding lid box, **When** the box and lid are generated, **Then** the lid's leading end carries a slight chamfer so it starts into the dovetail grooves without catching on their mouths.
3. **Given** a sliding lid box, **When** the box and lid are generated, **Then** the stop wall carries a dovetail matching the two sides — full thickness at the channel opening, half at the channel floor — and the lid's leading end is tapered to match, so the closed lid seats in it and cannot be lifted at the back; and at every point along the slide the lid and the body share no volume, so it seats without being forced.
3a. **Given** a sliding lid box, **When** the lid is generated, **Then** its vertical corners are rounded and both horizontal edges of its leading end are chamfered, so it starts into the grooves rather than snagging on their mouths.
3b. **Given** a sliding lid box asked for a catch, **When** the box and lid are generated, **Then** the catch is a **bump and dimple**: a dimple in the wall beside the outlet and a matching bump on the lid that drops into it as the lid closes — never a wedge.
4. **Given** a sliding lid box with a configured clearance, **When** the box and lid are generated, **Then** the lid is cut smaller than its groove by that clearance on every mating face so it slides smoothly — defaulting to 0.1mm per side.
5. **Given** the user selects a hinged lid box type, **When** the box and lid are generated, **Then** the lid pivots on an integrated hinge at the back, opens to at least 180 degrees, and stays attached.
6. **Given** the user selects a cap lid box type, **When** the box and lid are generated, **Then** the lid fits over the box walls with a friction-fit tolerance and can be removed by lifting.
6a. **Given** a cap lid box, **When** the body is generated, **Then** all four corners carry a smooth finger cutout below the skirt, so there is somewhere to push the lid off from; each cutout runs at least 10mm along each of its two sides, its profile is flat-top → radius → straight → radius → flat-exit with 2mm rolling in at the top and 2mm rolling out at the bottom, and a 2mm foot of full-thickness body remains below it.
6b. **Given** a cap lid box too short to fit that profile, **When** the box is generated, **Then** the library raises an error naming the shortfall and recommending a slipover box, rather than emitting a cap box with no way to open it.
7. **Given** the user selects a magnetic lid box type, **When** the box and lid are generated, **Then** cavities for magnets are placed in the lid and box walls at matching positions.
8. **Given** a sliding lid box, **When** compartments are also specified, **Then** the compartments do not interfere with the lid's sliding track.
9. **Given** a no-lid box, **When** the box is generated, **Then** a finger hole is cut into each of the two walls whose span is the box's longer horizontal dimension, sized to admit a fingertip: radius `min(20, min(length, width) / 4, height - floor_thickness + 1)`, reach `max(min(radius, height - floor_thickness - wall_thickness - 1), 2)`, and a 3mm mouth rounding, so the open tray can be lifted from either end (FR-047).

### User Story 3 - Finger Cutouts for Easy Piece Removal (Priority: P2)

The designer wants pieces inside each compartment to be easy to remove. They specify finger cutouts -- either scooped into the compartment wall/floor or placed on the box side walls. The library places these cutouts at the specified locations relative to each compartment or box side.

**Why this priority**: Finger cutouts are essential for usability but the box is functional without them (pieces can be tipped out). Depends on compartments/box being generated first.

**Independent Test**: Can be tested by generating a compartment with a finger scoop and verifying a fingertip fits: a 14mm-wide prism, standing on the cut's flat bottom, is entirely inside the removed material. (Intersection is not the test — a sphere of any size intersects almost any cut; containment is.)

**Acceptance Scenarios**:

1. **Given** a compartment with a finger scoop specified on its front wall, **When** the box is generated, **Then** a rounded cutout appears at the top of that compartment wall, sized to admit a fingertip.
2. **Given** finger holes specified on the box exterior (e.g., left and right sides), **When** the box is generated, **Then** a rolled cutout appears in each named wall, hanging from the top of the interior rather than from the outer rim, and reaching down by its own radius (FR-064).
3. **Given** a shallow compartment (under **5mm** deep), **When** a finger cutout is requested, **Then** the library automatically uses a **floor** scoop instead of a wall notch, because a notch in a well that shallow gives a finger nothing to bite on; the floor scoop's bowl is tangent to the floor and does not breach it (FR-062).

### User Story 4 - Automatic Compartment Layout (Priority: P2)

The designer provides a list of compartments with sizes but no positions. The library automatically arranges them to fill the box interior, respecting padding between compartments, grouping related compartments together, and maximizing space utilization.

**Why this priority**: Manual layout is tedious for many compartments. Automation saves significant design time. Can be tested independently of lid types.

**Independent Test**: Give the library 10 compartments of varying sizes and verify all are placed within the interior without overlaps, with consistent wall spacing, and the layout is deterministic.

**Acceptance Scenarios**:

1. **Given** 5 compartments with specified sizes and no positions, **When** the box is generated with automatic layout, **Then** all 5 compartments are arranged in rows within the interior, separated by walls of the correct thickness, and no manual coordinates were required.
2. **Given** compartments marked as a group (e.g., "card slot + token well must stay together"), **When** automatic layout runs, **Then** grouped compartments are placed adjacent to each other before other compartments fill remaining space.
3. **Given** compartments totaling more interior area than the box provides, **When** automatic layout runs, **Then** the library reports which compartment group overflows and by how much.

### User Story 5 - Nested Boxes: Sub-Boxes Inside a Game Box (Priority: P3)

The designer wants multiple sub-boxes (tuck boxes, card boxes) to nest inside a larger game box. They specify the outer game box dimensions and a list of sub-box specifications. The library computes whether the sub-boxes fit inside the outer box and generates all the pieces.

**Why this priority**: This is an advanced orchestration feature. A designer can manually check fit and place sub-boxes, but automation makes it practical for complex inserts.

**Independent Test**: Define an outer box and 4 sub-boxes of known dimensions; verify the generated sub-boxes all fit within the outer box interior without overlapping each other or the walls.

**Acceptance Scenarios**:

1. **Given** an outer box of 300x300x80mm and 4 sub-box specs (two card boxes 100x70x70mm, two token boxes 80x80x30mm), **When** nesting is computed, **Then** all 4 sub-boxes are arranged within the outer interior, and all can be lifted out by their finger cutouts.
2. **Given** sub-boxes that cannot all fit in the outer box, **When** nesting is computed, **Then** the library reports which sub-boxes cannot fit and by how much area or height they exceed the available space.
3. **Given** sub-boxes that must stand upright (height constraint), **When** nested layout is computed, **Then** all sub-boxes are placed with their openings facing upward, never on their sides.

### User Story 7 - Auto-Size Sub-Boxes and Fill Gaps with Spacers (Priority: P2)

The designer specifies multiple sub-boxes to go inside a game box, each with minimum dimensions. The library automatically expands boxes to fill their rows, aligns box lengths within each row, and fills any remaining empty space with hollow spacer trays. If a gap is smaller than 10mm, the adjacent box absorbs it rather than creating a tiny spacer.

**Why this priority**: Auto-sizing eliminates manual trial-and-error fitting of sub-boxes into a game box. Combined with the row-alignment behavior, it produces a clean, modular insert that is easy to load and unload. Depends on the nesting framework (FR-010).

**Independent Test**: Define an outer box of 300x200x80mm and 4 sub-boxes with minimum sizes; verify all boxes are expanded to fill their rows, boxes in each row share the same length, and any leftover gaps under 10mm are absorbed. Verify that gaps larger than 10mm produce spacer trays.

**Acceptance Scenarios**:

1. **Given** an outer box 300x200x80mm with 3 sub-boxes (min 90x80mm) that fit in one row, **When** auto-sizing runs, **Then** each box expands to fill the row width, all share the same length, and no spacer boxes are generated because the row is fully filled.
2. **Given** sub-boxes arranged in two rows where the second row leaves a 25mm-wide gap after expansion, **When** auto-sizing runs, **Then** a hollow spacer tray of 25mm width and matching height is generated to fill the gap.
3. **Given** a 7mm leftover gap in a row (below the 10mm threshold), **When** auto-sizing runs, **Then** the gap is absorbed by the nearest expandable box in that row rather than generating a spacer tray.
4. **Given** a spacer tray that would be less than 15mm in width or length, **When** auto-sizing checks the spacer, **Then** the space is instead absorbed by adjacent boxes since spacers cannot be smaller than 15mm in width or length.
5. **Given** sub-boxes of varying heights within a row, **When** the row's common length is computed, **Then** the height of shorter boxes does not affect the row length -- only the 2D footprint matters for alignment.

### User Story 8 - Export 3MF Files with Content-Based Caching (Priority: P2)

The designer generates a complete board game insert and needs printable 3MF files for their slicer. The library exports each box body and each lid as separate 3MF files -- both multi-color (with per-material assignments for MMU printers) and single-color (for single-extruder printers). For game boxes with nested sub-boxes, all sub-boxes and spacers are also exported. Unchanged files are not rewritten to disk -- only models whose geometry actually changed are updated, using a 3D Hausdorff distance comparison.

**Why this priority**: 3MF is the standard slicer interchange format for multi-material prints. Without export, the library only exists in-memory. Content-based caching prevents unnecessary file churn when iterating on unrelated parts of a layout.

**Independent Test**: Generate a BoxKit with 2 sub-boxes, export all files, modify only one sub-box, and verify that only the changed box's 3MF files are rewritten while unchanged files keep their original timestamps.

**Acceptance Scenarios**:

1. **Given** a single box with MMU inserts (different colored compartments), **When** exported, **Then** two 3MF files are produced: `<label>_body.3mf` and `<label>_lid.3mf`, each containing all materials/colors embedded in a single file. Additionally, single-color variants `<label>_body_single.3mf` and `<label>_lid_single.3mf` are produced.
2. **Given** a BoxKit with 3 sub-boxes and 2 spacer trays, **When** exported, **Then** the outer box produces body+lid 3MF files, each sub-box produces body+lid 3MF files, and each spacer tray produces its own 3MF file -- all in both multi-color and single-color variants.
3. **Given** a previously exported box whose geometry has not changed, **When** re-exported, **Then** the 3MF file on disk is NOT overwritten -- the Hausdorff distance between old and new mesh is below the tolerance threshold.
4. **Given** a box whose compartment layout changed (different sizes), **When** re-exported, **Then** the 3MF file IS rewritten because the Hausdorff distance exceeds the tolerance.

### User Story 9 - Decorate Lids with Labels, Patterns, and Print-Optimized Color Layers (Priority: P2)

The designer wants each box lid to look polished and be easy to print. They set a label text that auto-sizes to fill the lid face. The label can be framed (with a rectangular border, diagonal hatching behind the text for bed adhesion, and a color-accented top layer) or frameless (just the text). Text can be oriented corner-to-corner across the lid. A surface pattern (hex grid, grid, Voronoi, or tessellation) cuts through the lid as decorative through-holes, saving filament. Three independently settable accent colors control the label text, the frame top layer, and the pattern top layer. If the computed text height falls below a configurable minimum (default 4mm), the label is skipped.

**Why this priority**: Lids are the most visible part of a board game insert. Decoration makes the output presentable. The color-layer architecture and minimum-text-size guard prevent print failures and wasted filament. Depends on lid geometry generation (P1).

**Independent Test**: Create a box with lid text "Animals", a hex-grid lid pattern with through-holes, a framed label with diagonal hatching, and verify the 3MF contains exactly the expected color assignments and the text auto-sizes to fill the lid.

**Acceptance Scenarios**:

1. **Given** a lid of 100x70mm with label text "Cards", **When** the lid is generated with auto-sizing, **Then** the text is scaled to fill the lid area minus a 5mm border margin, and the computed text height is ≥ 4mm.
2. **Given** a lid of 40x30mm with label text "Tokens", **When** the auto-sized text height computes to 3mm (below the 4mm minimum), **Then** the label is skipped and the lid prints as a plain decorated lid with no text.
3. **Given** a framed label with accent frame color set to gold and label text color set to white, **When** the lid is exported as multi-color 3MF, **Then** the frame top layer is assigned the gold material and the text is assigned the white material.
4. **Given** a lid with a hex-grid pattern, **When** the lid is generated, **Then** hexagonal through-holes are cut through the lid surface following the pattern grid, saving filament in the open areas.
5. **Given** a lid with corner-to-corner diagonal text orientation on a non-square lid, **When** the text is placed, **Then** the text runs from one corner of the lid to the opposite corner at the natural angle (not forced to 45°).
6. **Given** a framed diagonal label, **When** the lid is generated, **Then** diagonal hatching lines fill the rectangular frame behind the text to provide bed adhesion support for text islands, and a small outer border surrounds the frame.

### User Story 10 - Generate Packing Layout PDF Guide (Priority: P3)

After generating all box pieces, the designer needs a visual guide showing exactly where each box goes inside the game box. The system produces a PDF packing guide on exactly one page. It MUST NOT use a flat top-down or side view. Instead, it MUST use a 3D isometric/oblique angle view (looking slightly from above and to the side of the box) so the interior depth and vertical layers are clearly visible. The guide MUST show a step-by-step breakdown of how the box is filled up, pulling the top-level stacked boxes out of the project box (using vertical Z-displacement and arrows) to reveal the lower-level boxes at the base, progressing step-by-step or showing a clear exploded assembly view on the single page. The PDF is generated automatically on export but only regenerated if the layout changed (cached by SHA-256 hash of the layout + library version).

**Why this priority**: A packing guide is essential documentation for anyone assembling the insert — they need to know which box goes where, in what order. Cached regeneration avoids unnecessary PDF rebuilds during iterative development. Depends on the full packing/export pipeline being complete (P2).

**Independent Test**: Export a 4-box game, verify a PDF exists in the output directory, verify it shows 4 labeled boxes in correct positions with packing order numbered.

**Acceptance Scenarios**:

1. **Given** a Project with 4 sub-boxes packed into a 300x200mm game box, **When** `project.export()` runs, **Then** a PDF is produced in `{out_dir}/{project.name}/layout.pdf` on exactly one page, showing the game box outline in a 3D oblique/isometric projection, each sub-box at its packed position with label and dimensions, and spacer trays marked.
2. **Given** a multi-layer stacked layout, **When** the PDF is viewed, **Then** it shows a 3D exploded view with stacked upper boxes pulled upward along the Z-axis with dashed lines/arrows showing their placement positions, clearly revealing the lower-level boxes at the base.
3. **Given** a previously exported layout with no changes, **When** `project.export()` runs again, **Then** the PDF is NOT regenerated — it is skipped along with unchanged 3MF files.
4. **Given** a layout change (different box sizes or positions), **When** `project.export()` runs, **Then** the PDF IS regenerated to reflect the new layout.

### User Story 6 - Custom Compartment Layout (Manual Positioning) (Priority: P3)

The designer wants precise control over compartment placement. They specify exact X, Y coordinates for each compartment within the box interior, overriding automatic layout.

**Why this priority**: Power users need manual control for bespoke designs. Automatic layout (P2) handles the common case; manual positioning handles the edge cases.

**Independent Test**: Specify compartment positions explicitly and verify generated compartments appear at those coordinates relative to the box origin.

**Acceptance Scenarios**:

1. **Given** compartments with explicit (x, y) positions in the interior frame, **When** the box is generated, **Then** each compartment is placed at its specified position, and no automatic repositioning occurs.
2. **Given** a compartment manually positioned to overlap another, **When** the box is generated, **Then** the library warns or errors about the overlap rather than silently producing invalid geometry.

### Edge Cases

- What happens when a compartment depth exceeds the box interior height? The library must reject the configuration with a clear error.
- What happens when finger cutouts intersect each other or a compartment corner? The library must detect and warn about overlapping cutouts (FR-006c).
- How does the system handle zero-thickness walls (open compartments sharing a boundary)? The compartments merge into a single cavity.
- What happens when a nested sub-box has its own lid that increases its effective height? The lid thickness must be included in the nesting height check.
- How does the library handle non-rectangular box outlines (polygon-shaped boxes)? Compartments and sub-boxes must fit within the polygonal interior boundary.
- What happens with a hinged box that has compartments extending into the hinge area? The hinge knuckles must clear the compartment walls.
- What happens when all sub-boxes have minimum dimensions that collectively exceed the outer box interior? The library must reject the configuration at spec time with a descriptive error listing each over-constrained box.
- What happens when a row's gap is large enough for a spacer (>10mm) but the spacer width would be under 15mm? The gap is absorbed by the adjacent box -- spacer minimum dimensions (15mm W/L) take precedence over the gap threshold.
- What happens when one box in a row has a fixed (non-expandable) dimension that is shorter than the row's common length? The box keeps its fixed dimension; the row length still matches the longest box, leaving a gap for spacers beside the shorter box.
- What happens when spacer trays have a height under 5mm? They are permitted -- spacer trays can be shorter than 5mm in height (unlike width/length which has a 15mm minimum).
- What happens when a 3MF file already exists on disk but the exported mesh is empty (no geometry)? The file is NOT written; a warning is emitted.
- What happens when the Hausdorff distance tolerance is too tight and floating-point noise triggers unnecessary rewrites? The tolerance defaults to a value large enough to absorb FP jitter (e.g., 0.001mm) but is user-configurable.
- What happens when the Hausdorff comparison file or `.layout_cache.json` is corrupted or unreadable? The corrupted file is treated as a cache miss — silently overwritten with regenerated data.
- What happens when exporting a box with no lid (a no-lid box type)? Only a body 3MF is produced; no lid 3MF is generated. If a `LidBuilder` is configured on a no-lid type, a warning is emitted and the lid decoration is silently dropped.
- What happens when the Project has no sub-boxes (empty)? No files are produced; `ExportResult` returns empty written/skipped lists and no PDF is generated.
- What happens when a box has no compartments AND no explicit `size`? A `ValueError` is raised — either compartments or an explicit size is required.
- What happens when a spacer tray's computed height is zero or negative due to a packing error? A `ValueError` is raised during spacer generation.
- What happens when min text height threshold is set to 0mm? All labels print regardless of computed size — a threshold of 0 disables the size guard.
- What happens when compartment width ratios sum to > 1.0 (e.g., three compartments each requesting 0.5 width ratio)? The system MUST reject the configuration with a descriptive error listing the over-allocated compartments and their individual ratios.
- What happens when `mmu_label` is specified but `single_label` is not (or vice versa)? The unspecified mode defaults to the parent `LidBuilder` configuration — per-mode overrides are optional, not required.
- What happens when a stackable box is stacked on a non-stackable box (or vice versa)? The interlocking rim is only generated on stackable boxes; stacking a stackable box on a plain box has no mating rim and the two do not interlock — this is a valid (non-nesting) configuration.
- What happens when magnet slots on opposing sides of a hex box would overlap at a corner? Magnet slots MUST be positioned to avoid corners; if the configured slot count exceeds the available straight-wall length, the library MUST reject the configuration with a descriptive error.
- What happens when a standalone box has `expandable=True`? Expansion is ignored — standalone boxes are not packed into a container, so `expandable` has no effect.
- What happens when a hex-grid compartment requests `rows` or `cols` of 0? The library MUST reject the configuration — `rows` and `cols` must both be positive integers.
- What happens when a hex tile is larger than the hex box interior? The derived hex grid bounds (rows × cols × cell size) are clipped to the box interior; a hex cell that would extend beyond the interior is clipped or omitted, and the layout is rejected if zero cells fit.
- What happens when both `push_block_height` and a floor finger hole are enabled on the same hex cell? The finger hole is offset to the cell edge (the pillar occupies the center), so the two never intersect.
- What happens when the 3D packer rotates a box but its compartments do not fit in the rotated interior? The library MUST re-run compartment layout in the rotated frame; if compartments still overflow the rotated interior, the box is rejected with a descriptive error (or the box is marked `no_rotate` so the packer only considers the original orientation).
- What happens when lid text auto-sizes below 4mm on a large lid but the text string is very short (e.g., "A")? The text is scaled until the character height hits the minimum; if it can't reach 4mm while fitting the lid, the label is skipped.
- What happens when a through-hole pattern intersects the label frame or text area? Through-holes are clipped to avoid the label area -- the label text and frame take precedence and pattern holes stop at the label boundary.
- What happens when the box body color and all three accent colors are set to the same value? The multi-color 3MF degenerates to a single material; it is still valid but the user gets a warning that no visible color contrast exists.
- What happens when the game box has no sub-boxes (empty Project)? No PDF is generated — the layout is trivially empty and there is nothing to pack.

## Requirements

### The Governing Principle: Good Defaults, Not Options

Everything below is subordinate to this. **The API must be as simple as it can be, and must choose good defaults so that in the ordinary case the user changes nothing.** A user should be able to describe what goes in the box — sizes, compartments, a label — and get printable files end to end, without tuning geometry they did not ask about.

- **FR-000**: Every geometric parameter MUST have a default that produces a **correct, printable, good-looking** result on its own. A default that merely avoids an error is not a default; it is a trap that ships. Defaults MUST be derived from what is already known — the wall thickness, the box's height, the piece being held — rather than fixed constants, so that they stay right across the range of boxes people actually build.
- **FR-000a**: The **common path MUST require no overrides**. Choosing a box type, giving a size and listing contents MUST be enough. Any feature that only works once the user has set an option is a feature that does not work; if a parameter has to be set for the result to be usable, its default is wrong and MUST be fixed rather than documented.
- **FR-000b**: Overrides MUST remain available for the unusual case, but MUST be **additive and local** — one named parameter changing one thing. The library MUST NOT require a user to set several parameters consistently for any single outcome, nor to understand the geometry's internals to pick a value. Where two parameters must agree, the library MUST derive one from the other rather than asking for both.
- **FR-000c**: When the defaults genuinely cannot produce a good result at the size requested, the library MUST **say so and name the alternative** (as a too-short cap box does, FR-002n) rather than silently emitting a degraded part. Refusing with a useful message is part of working out of the box; producing something unusable is not.
- **FR-000d**: The end-to-end path — describe, build, preview, export — MUST work **without extra steps** between the stages. No manual regeneration, no separate configuration file, no post-processing pass the user has to remember.
- **FR-000e**: Every geometric default MUST be declared **once**, as a field default on the box description (`BoxSpec`), and no function may carry a fallback of its own. A default stated twice is two defaults and they will differ: read from a dict, `wall_thickness` was restated at 36 call sites, `lid_thickness` at 33 and `floor_thickness` at 23, and the copies drifted — a hinge came to be built with five knuckles by the geometry and three by the builder configuring it. Where a **type** genuinely needs a different value (a sliding-catch box always carries a catch, a plain sliding box carries none) the type resolves the description's `None`; it does not restate the number as a second default.
- **FR-000f**: A parameter the library does not read MUST NOT be accepted. A keyword that is documented, exported and ignored is worse than a missing feature: `two_layer=True` on a sliding box was set by a shipped example and changed nothing, and nothing in the geometry or the output said so. Passing a keyword the box type has no field for MUST raise, naming the field and listing the valid ones.
- **FR-000g**: A named option MUST do the thing it is named after, or not exist. Silently substituting a different behaviour — a lid pattern falling back to square holes because the module that draws it is absent — leaves the user with a plausible result and no way to learn the request was dropped. Where the library cannot honour a named option it MUST raise (FR-000c), never substitute.
- **FR-000h**: **The library MUST NOT fail silently.** Where it cannot do what was asked it MUST raise, naming what failed. It MUST NOT produce nothing and report success, and it MUST NOT substitute a quieter wrong answer for a loud failure. This is FR-000g applied to the failure path rather than the option path, and it was the more damaging of the two, because what it produced looked like a finished export:
  - A missing geometry backend returned `None` from every builder, `False` from the exporter, and an export that created the whole directory tree, wrote a **0-byte 3MF per piece**, recorded each one as written, and exited 0. A broken install was indistinguishable from a successful run until the files reached a slicer.
  - A missing dependency MUST be reported by name, with what it was needed for and how to install it — the three things a user needs to fix it. pybosl2, the geometry backend and fpdf are all **required**; none of them is optional, so none may be answered by degrading.
  - An `ImportError` swallowed mid-build produced a box with **no compartments carved into it**, and one swallowed in the lid path produced every lid **blank** — no label, no pattern — with nothing said in either case.
  - A piece that builds no geometry MUST raise rather than export an empty file. A spacer that fails to build MUST NOT be dropped from the layout, a colour that cannot be applied MUST NOT be silently discarded, and a layout sheet that fails to draw MUST NOT be skipped as "best-effort".
  - A box sized from its contents MUST NOT fall back to an **estimate** when the real measurement raises. A wrong number that looks like a measurement is worse than an error, because the box is then built to it.
  - The exception is a cache: a corrupt or unwritable fingerprint record MUST be treated as a miss and regenerated, because that loses no output and the next run is correct.

### Functional Requirements

- **FR-001**: The library MUST accept outer box dimensions (width, length, height) and generate a 3D model of a closed box with a user-selected lid type.
- **FR-002**: The library MUST support at least these lid types: sliding lid, cap lid (friction-fit), hinged lid, and filament-hinge lid, each producing correct mating geometry between lid and body.
- **FR-002a**: A sliding-lid box MUST have an **open end** for its lid to enter. The lid's channel MUST run out through one end wall, and the opposite end wall MUST remain as the stop the closed lid seats against. A box with grooves but no opening is one the lid can only be dropped into, which is not a sliding box.
- **FR-002b**: A sliding lid MUST leave through the box's **shorter** face — that is, slide along the longer horizontal axis. The grooves then run along the box's long walls, where there is most material to carry them, and the opening is the narrow end a card box is designed to be opened from.
- **FR-002r**: A hinge MUST sit **inside** the box's declared outline — barrel, knuckles and leaf webs alike. No box type may place material outside the size it declares, hinges included: a box that hangs a barrel off its back cannot be packed against its neighbours, and the packer has no way to know it should reserve the space.
- **FR-002c**: A sliding lid's two long edges MUST carry an **angled dovetail** for the full sliding length. In cross-section (perpendicular to the slide axis) the lid is a trapezoid whose **top** face is the box interior (the box width minus **twice** the wall thickness — no key at the top) and whose **bottom** face reaches **half the wall width** into each wall, the two joined by straight angled flanks. The groove is wider at its floor than at its opening — so the lid is trapped and can slide along the axis but cannot be lifted straight out — and it never reaches the outer face, so half the wall always remains behind it for support. The two long box walls MUST carry the matching mirror-image dovetail groove, so the lid and its groove are the same shape.
- **FR-002s**: Because the hinge is inside, it MUST be **carved out of the interior mask** — the volume compartments and contents may occupy. The mask MUST use a clearance cylinder for the barrel and a support web that angles back to meet the back wall of the box, so that a rounded/scooped compartment next to the hinge has the correct inside slope while keeping the hinge solid. This is what the original toolkit's `FilamentBoxInsideMask` does for the filament hinge.
- **FR-002d**: The sliding lid's **leading end** — the end that enters the box's open end first — MUST carry a slight **chamfer** on **both** its horizontal edges: the underside one keeps the thin leading lip off the groove floor, the top one keeps the lid's top corner off the wall lip at the mouth. The chamfer MUST be *slight* — a quarter of the lid's thickness by default, and settable. Half the thickness takes a 2mm lid down to a 1mm knife edge, which is a wedge, and a sliding lid may not have one (FR-002e0). The dovetail flanks MUST stay square: the chamfer is a lead-in, not a roundover.
- **FR-002t**: Each half of a hinge MUST be **relieved out of the other**. With the hinge inside the box, each half's knuckles occupy space the other half's material would otherwise fill; relieving only one side leaves the two fused as surely as relieving neither.
- **FR-002e**: A sliding-lid box MUST carry a **dovetail in its stop wall** (the wall opposite the open end), cut to the same depth as the two sides — full thickness at the channel opening, **half of it** at the channel floor — and the lid's leading end MUST be tapered to match, so the lid seats in that groove instead of butting against a flat face. Without it the lid's leading end rests on nothing and stands proud at the back.
- **FR-002e0**: That back groove is a **seat, not a catch**, and the difference MUST hold geometrically: because the lid's leading taper matches the seat's, the two faces stay parallel with the slide clearance between them for the whole travel. At **no point** along the slide may the lid and the body share any volume. A **wedge catch** — a taper the lid must be forced past to close and sprung back out to open — is forbidden anywhere on a sliding box: it loads the thin leading lip in exactly the direction 3D-printed layers split. A matched taper and a wedge look alike in a render, so the requirement is stated as the travel, which distinguishes them.
- **FR-002e1**: A sliding-lid box MAY carry a **bump catch** to hold the closed lid shut. A bump catch is a hemispherical **dimple** in the box and a matching **bump** on the lid that drops into it as the lid reaches the stop. Nothing has to deform to pass it beyond the small elastic click the bump's own height demands, and the bump loads the lid across its thickness rather than peeling its leading lip.
- **FR-002e2**: The dimple MUST sit in the wall **beside the outlet** — the mouth the lid enters and leaves by — and the bump on the trailing end of the lid, so the catch engages only in the last few millimetres of travel. Putting the catch at the closed end means dragging the bump the whole length of the groove on every open and close, wearing the groove and making a short lid hard to start.
- **FR-002e3**: The dimple MUST be cut **larger than the bump** by a fit clearance, so the two click rather than jam, and the catch MUST be sized by a settable radius. A sliding box MUST default to **no catch** (a plain sliding lid, as the original toolkit's); a sliding-catch box MUST always carry one.
- **FR-002e4**: The sliding lid's **vertical corners** MUST be rounded, so the corners that go in first do not snag on the groove mouths as the lid is offered up. The radius MUST default to a fraction of the wall thickness, MUST be capped at the dovetail's depth so it cannot eat the key that retains the lid, and MUST be settable per box.
- **FR-002e5**: A sliding lid MUST carry a **fingernail catch**: a shallow spherical dish in its top face, at the end the lid comes out of, that a fingernail hooks into to start it moving.
  - A seated sliding lid is a plate flush with the box's top, held in its grooves. There is nothing to grip: the only exposed surfaces are its end face — a lid thickness tall — and its top, which is smooth. What actually gets such a lid open is a nail in a dish, so the dish is part of the type, not an option (FR-000a).
  - It MUST be **half** the top of a sphere, split on a plane square to the slide axis: a bowl on the inboard side, and a **flat wall** across the pull on the outboard side. The two halves do different jobs. The bowl is what the nail goes into — a surface curving away in every direction, so the nail finds it without being aimed, where a cylindrical pocket would present a rim for the nail to catch on instead of dropping in. The wall is what the nail then pulls on, and it MUST be flat: a whole dish curves away on the pull side too, so a nail loading it is riding up a slope and skids out of the dish rather than moving the lid.
  - The half that is kept MUST be the **inboard** one, so the wall has the lid's material behind it in the direction of travel. A nail can push and not pull: it moves the lid by pressing the wall towards the exit, and that only works if the wall is the one between the dish and the exit edge. Keeping the other half gives a wall that can only be pushed inboard, which drives the lid further into the box.
  - The split MUST pass through the sphere's centre, so the wall is the full depth of the dish rather than a sliver of it.
  - It MUST sit at the **exit end** — the end that finishes outside the closed box, and the only end a hand can reach — and be centred across the lid, so pulling it draws the lid straight rather than skewing it in its grooves.
  - Its wall MUST stand **on the lid's border line**, so the band of plain lid at the edge is the material the nail presses on and the bowl lies inside it. The catch belongs at the edge, where the fingers are.
  - It MUST NOT pierce the lid. Its depth MUST default to at most **half the lid's thickness**, so a plate's worth of material always remains under it.
  - A **1mm margin of solid lid** MUST be kept around it, clear of any pattern. The dish is a thinned part of the plate and it is pulled on, so it needs the material around it intact to pull against; a hole opening straight onto its rim is where the lid would tear.
  - Its size MUST be derived — from the lid's own width and thickness — and MUST be settable per box, and a box MUST be able to decline it.
- **FR-002u**: A **slipover sleeve MUST carry corner finger notches** so it can be pulled off. A sleeve is otherwise a smooth box: it covers the body on four sides and its faces are flush, leaving nowhere to get a fingertip. The notches MUST be at two **diagonally opposite** corners, so a pair of fingers pulls along the sleeve's axis rather than twisting it, and MUST sit just below the lid plate, where the notch exposes the body's corner to be pushed out.
- **FR-002f**: The sliding lid MUST be cut with a **clearance** on every mating face so it slides smoothly, and that clearance MUST be configurable, defaulting to **0.1mm** per side.
- **FR-002g**: A corner notch MUST be built from the **same finger-scoop geometry** as every other finger cut in the library — the original composes it from two `FingerHoleWall` scoops meeting at the corner — so it inherits the roll, the floor fillet and the face fillets rather than reimplementing them and drifting.
- **FR-002v**: A hinged box or filament hinged box MUST carry a **snap-fit catch at the front wall** to hold the lid closed. The catch height MUST be at most **half the box height**. By default, it uses a **ridge catch** with a right-angled triangular profile: the bottom of the ridge is sloped (angled lead-in) so it slides into the pocket, while the top of the ridge is flat/horizontal to catch and lock in place. The cut pocket into the body wall has a depth in Y of **half the wall thickness**, and the wider V-shaped triangular protrusion (bead) resides on the lid's matching tab. Alternatively, a **bump catch** is supported, consisting of two side-by-side round bumps on the lid tab that snap into two matching hemispherical indents inside the pocket on the box body. The lid tab MUST have **smoothed vertical corners** (at least 1mm radius or chamfer) to prevent sharp edges. The top of the lid tab MUST have an **angled strengthening piece** (gusset/support) that slopes up and back to meet the bottom face of the lid, and the box body's front wall MUST have a **matching clearance pocket carve-out** on its inside top edge to accommodate this gusset when closed.
- **FR-002h**: The notch's height MUST default to **half the skirt's height** (capped at 20mm), and its radius to the larger of that height and a fingertip minimum, so a shallow sleeve still gets a usable grip. Both MUST be settable per box.
- **FR-002i**: A **cap box's body MUST carry a finger cutout at every one of its four corners**, cut into the band just below the lid's skirt, as the original toolkit's cap box does. A cap lid is a friction fit over a smooth body: with nothing to get a fingertip behind, the only way off is to prise at the seam. The corners are where two cutouts meet, so a finger pushing there loads the lid along both faces at once.
- **FR-002j**: A corner cutout MUST be built from the **same finger-scoop geometry** as every other finger cut in the library — two wall scoops meeting at the corner, as `CornerCatch` does — so it inherits the roll, the fillets and the face treatment rather than reimplementing them.
- **FR-002k**: The cutout's profile, in elevation along each side, MUST be **flat top → first radius → perpendicular flat middle → second radius → flat exit**. The two radii together MUST be at least **4mm** — 2mm rolling in at the top and 2mm rolling out at the bottom — and MUST **grow to 6mm where the box can spare the height**, which is a gentler curve under a fingertip. 4mm is a floor, not a target: the same cutout suits a 12mm box and a 60mm one only if it can breathe on the taller one, and growing it MUST NOT raise the minimum box size. The budget is stated as a **total** because it is the total that competes with the box's height. "Where the box can spare the height" MUST be read as a rule, not a judgement: the total is `min(6, max(4, height - lid_thickness - skirt - foot))` — every millimetre the box has beyond FR-002n's minimum goes to the curve until it reaches 6mm, and none of it before.
- **FR-002l**: A **2mm foot** of full-thickness body MUST remain below the cutout. The cut is a recess in the side of the box, not a through-slot: without a foot the body's wall is severed at the corner, which is the corner the box is stacked and dropped on.
- **FR-002m**: Each cutout MUST run at least **10mm** along each of its two sides — a fingertip's width — and at most **one sixth** of that side's length, so the band the skirt grips keeps most of its bearing. Where a sixth of the side is under 10mm the minimum wins: 10mm is what a finger physically needs, while a sixth is a preference about grip.
- **FR-002m1**: A cap or slipover box whose **footprint** cannot carry those cutouts MUST be refused the same way a too-short one is (FR-002n). Two cutouts meet at each corner of every side, so a side needs `2 × 10mm` of cutout plus a run of uncut band between them; below that the corner cuts merge into one continuous slot and the skirt loses its bearing along the whole face. The height check alone lets a 30 × 30mm box through and produces exactly that.
- **FR-002n**: The smallest cap box that can carry the cutout is therefore **lid thickness + 3mm skirt + 4mm of curve + 2mm foot**, read down the box. Below that the library MUST **raise an error** naming the box's height, that minimum, each term of it, and recommending a **slipover box** instead. Silently shrinking the radii produces a cap box whose lid cannot be got off, which is worse than refusing to build it; a slipover of the same size opens by its corner notches (FR-002u).
- **FR-002n1**: A cap lid's **skirt MUST be at least 3mm** where the body is cut for finger holds — the grip the lid is held by at the corner being pushed. The skirt's default (half the box height, capped at 10mm) MUST additionally be **capped so the cutout below it still fits**: half the height is a fine skirt on a tall box and swallows a short one whole. A tall box's skirt MUST be unaffected.
- **FR-002o**: A slipover **sleeve's wall MUST be half** the box's wall thickness. The sleeve is a skin over a body that already has a full wall behind it everywhere the sleeve touches, so a full-thickness sleeve is a second wall carrying nothing: it costs the interior two full walls of width across every axis and prints a part twice as heavy as the job needs.
- **FR-002p**: A slipover sleeve MUST stop **short of the foot**, leaving a band of body showing all the way round for the fingers to pull on. The sleeve's skirt is therefore `height - foot - gap`, where the gap defaults to `min(6, max(3, (height - foot) / 4))` — a quarter of the **covered** height, held between 3mm and 6mm — wider where the box can spare it, because a wider gap takes a wider curve. This gap is the band the fingers pull on and is a different feature from the corner notches of FR-002u/h, which cut into the sleeve itself; a sleeve has both.
- **FR-002q**: A cap box's corner indent MUST be cut **exactly as deep as the lid's own offset** — the step the band above it is already set in by — so the recess and the skirt lie in the same plane and a finger meets one continuous surface. An indent shallower than the offset leaves a lip between the two for a fingernail to catch on; a deeper one undercuts the band the skirt grips.
- **FR-003**: The library MUST allow users to define interior compartments by specifying dimensions (width, length, depth) either as absolute values (e.g., `size=(50.5, 70.2)`) or as ratios of the box interior dimensions (e.g., `width_ratio=0.5` takes 50% of the interior width). All dimensions MUST maintain 0.1mm precision — no rounding to whole millimetres.
- **FR-003b**: A compartment given **no size** MUST fill the interior, and one given **no depth** MUST run to the box's floor. Filling is what a well normally does, so it is what happens when nothing is said (FR-000). The alternatives shipped were a fixed 50mm footprint and a fixed 10mm depth, which are right for no box in particular; and because they were wrong for every box, the examples wrote the arithmetic out at the call site — `size - 2 × wall`, `height - floor - lid` — which is the library's own geometry, restated by the user.
  - A box whose compartments **all** fill and which has no size of its own MUST be refused with a message naming the box and its wells: nothing can be derived from a well that only fills.
- **FR-003c**: A **ratio MUST be read against the room compartments actually have**, not against the raw interior. The auto-layout puts a wall's spacing before, between and after them, so N wells asking for `1/N` each have to share `interior − (N+1) × spacing`. Measured against the raw interior, ratios summing to exactly 1.0 — which FR-003a explicitly permits — overflowed every time, and the only way to divide a box evenly was to guess the layout's spacing at the call site (FR-000b).
- **FR-003d**: A compartment whose size was **derived from the interior** — a ratio or a bare fill — MUST NOT then be rotated by the layout. Its width was measured on the box's width axis, so rotating it asks the length to hold a number worked out for the width.
- **FR-003a**: When any compartment uses ratio-based sizing, the sum of all compartment width ratios in a row MUST NOT exceed 1.0, and the sum of length ratios MUST NOT exceed the available length per row. The library MUST validate this at specification time and reject configurations where ratios overflow.
- **FR-004**: The library MUST provide automatic compartment layout that arranges compartments in the interior without overlaps, respecting wall thickness between adjacent compartments and between compartments and box walls. The layout engine MUST support rotating compartments by 90 degrees during bin-packing to optimize space utilization.
- **FR-004a**: The layout engine MUST support bin-packing for non-rectangular compartment shapes (such as hexagons, circular slots, or custom polygonal/silhouette shapes like those in Emberleaf). The engine MUST utilize the bounding box of these non-rectangular shapes to determine placement constraints, ensuring they are packed without overlaps.
- **FR-004b**: The library MUST support element packing inside a bounding box, where multiple instances of a shape (such as worker or hero tokens) are arranged inside a local bounding box using a set of X/Y offsets and rotation parameters. This bounding box is then treated as a single unified rectangular compartment or sub-box footprint for layout in the main box container.
- **FR-005**: The library MUST allow manual positioning of compartments by specifying explicit coordinates within the interior frame.
- **FR-006**: The library MUST support finger cuts in three places: through a **compartment wall**, into a **compartment floor**, and through a **box exterior wall**. The three share one geometry and one vocabulary (FR-006a); which of the first two a compartment gets is chosen by its depth (FR-062).
- **FR-006a**: The finger-cut requirements MUST be read with these terms, and the library MUST use them consistently in its API and its messages:
  - **edge scoop** — a cut *through* a wall, open at the top: flat bottom, throat, rolled mouth. The shape a finger is drawn along. Cut into a compartment wall or a box's exterior wall; the two differ only in where they are aligned (FR-064, FR-067).
  - **floor scoop** (a **bore**) — a cut into a compartment *floor*, tangent to it, that a piece is pushed up through. A different profile from an edge scoop and MUST NOT share it (FR-062).
  - **pull-out** — the dish across a silhouette slot that lets the piece be lifted (FR-078).
  - **corner notch** — the pair of edge scoops meeting at a corner of a cap body or a slipover sleeve (FR-002u, FR-002i).
  - **mouth** — the cut's opening at the top of the wall, `throat radius + mouth flare` wide on each side of centre.
  - **face fillet** — the rounding where a cut emerges on a face of the wall it passes through (FR-073).
  - The words *notch*, *cutout*, *dip* and *finger hole* are informal names for an edge scoop; the requirements MUST NOT use them to mean anything else.
- **FR-006b**: Every depth a finger cut is given MUST be measured from **the top of the wall it is cut into** down to **the deepest point of the material it removes**, and that deepest point is at the wall's *faces*, where the face fillet reaches furthest. Both ends of the cut follow from that one datum, so a cut asked for a 14mm reach removes material over exactly 14mm of height. Stating the datum is not pedantry: with the depth read to the outline instead, the face fillet puts the real cut a fillet deeper, and correcting that by moving the whole cut carries its mouth off the wall top by the same amount.
- **FR-006c**: The library MUST **detect finger cuts that overlap** — each other, a compartment wall, or a box feature such as a magnet pocket or a lid track — and MUST report them by name and position rather than silently emitting the merged cut. Two cuts that overlap do not produce two grips; they produce one hole of a shape nobody specified, and the geometry gives no sign of it.
- **FR-007**: The library MUST reject invalid configurations at specification time: compartments deeper than the interior height, compartments that cannot fit in the interior, overlapping manually positioned compartments.
- **FR-008**: The library MUST support grouping compartments so they are packed together during automatic layout, and support packing bins (best-fit, next-fit, with rotation) for arrangement strategy.
- **FR-008a**: The library MUST support sharing a list of compartments across multiple boxes using `project.share_compartments(boxes, compartments)`. The library MUST automatically partition and bin-pack these compartments across the specified boxes during export.
- **FR-009**: The library MUST generate all pieces as output -- box body, lid, and any separate sub-boxes -- with consistent material colouring and the same coordinate frame so they align when assembled.
- **FR-010**: The library MUST support nested sub-boxes: an outer box specification containing inner sub-box specifications, with the nesting layout automatically packed into the outer box interior.
- **FR-011**: The library MUST validate that all nested sub-boxes fit within the outer box interior (both footprint and height) before accepting the specification.
- **FR-012**: The library MUST support declaring minimum dimensions for each nested sub-box, allowing the box to auto-expand to fill available space in its row or column up to the outer box interior bounds. Box expansion MUST prioritize the X and Y axes. For the Z (height) axis, the library MUST prefer generating spacer boxes/trays to fill the empty space rather than expanding the box's height, unless the remaining height difference is less than a 3mm threshold.
- **FR-013**: The library MUST align sub-boxes into rows where every box in the same row shares a common length (the length of the longest box in that row), so rows are uniform and boxes are easy to place and remove.
- **FR-013a**: For the main Earth box layout, card boxes and player boxes MUST share an identical footprint of 68.0 x 99.0 mm, with primary card boxes fixed at 55.2mm in height to fit cleanly under the player boards. Smaller card and player boxes MUST stack exactly to 55.2mm to form uniform columns.
- **FR-013b**: When the 3D box packer rotates a sub-box by 90 degrees (swapping its width and length to fit the container), the compartment layout inside that box MUST be re-generated in the rotated interior frame. Compartments MUST be re-laid-out using the box's post-rotation interior dimensions, and the compartment orientation MUST follow the box's rotation so that contents stay correctly aligned with the box walls.
- **FR-013c**: The library MUST support a per-box `no_rotate` flag that marks a box as NOT rotatable. When `no_rotate` is set, the 3D packer MUST only consider the box's original (width, length) orientation and MUST NOT swap its dimensions; the compartment layout MUST always use the box's natural width/length without rotation. This is required for boxes whose contents are directionally constrained (e.g., card slots that must span a specific axis). `no_rotate` defaults to `False` so boxes rotate freely by default.
- **FR-014**: The library MUST generate hollow spacer boxes/trays to fill all open spaces and gaps in the 3D packing layout. Spacer boxes/trays MUST NOT be thinner than 5mm in any dimension (width, length, or height). For vertical gaps along the Z-axis, a spacer box MUST be generated if the gap height is >= 3mm (subject to the 5mm minimum thickness rule). If the gap height is < 3mm, the adjacent box's height MUST expand to absorb the gap. Spacer boxes MUST be shown in the layout PDF.
- **FR-014a**: The library MUST produce the **fewest spacers** that cover the leftover space. A void that could be filled by one tray MUST NOT be emitted as several. In particular, the packing pass MUST NOT split a void merely because some unrelated box elsewhere in the layout contributes a cut plane that happens to pass through it: the number of spacers MUST depend only on the shape of the empty space, not on how many boxes the layout contains or what order they were placed in.
- **FR-014b**: After the leftover space has been decomposed, the library MUST run a merge pass that repeatedly fuses any two spacers whose union is itself a box — that is, they touch face-to-face along one axis and match exactly on the other two — until no further merge is possible. The merge MUST be order-independent: the same layout MUST yield the same set of spacers regardless of the order the pieces were found in.
- **FR-014c**: Spacers MUST respect the same clearance slack as nested sub-boxes (FR-019). A spacer's footprint MUST be shrunk by the project's clearance slack so that it can be lifted in and out of the game box rather than being an interference fit against its neighbours.
- **FR-014d**: When the leftover space at one height forms a shape no rectangle covers — an L, T, U or similar — the library MUST emit it as a **single** spacer with a polygon footprint (a path box, FR-018) rather than as several rectangular trays. Only regions sharing an identical Z span may be combined this way.
- **FR-014e**: The library MUST NOT combine spacers that sit at different heights, even when their union would be a valid prism. Two stacked leftover regions each rest on whatever is beneath them; fusing them produces one part whose upper arm is an unsupported overhang, which is harder to print than the two trays it replaced. Vertical steps stay as separate spacers by design.
- **FR-015**: The library MUST absorb horizontal gaps (X and Y axes) smaller than the auto-fill threshold (default 10mm) into adjacent expandable boxes rather than generating spacer trays. Gaps exactly equal to the threshold generate spacer trays.
- **FR-016**: The library MUST use variable row widths: each row's width is determined by the widest box in that row after expansion, and rows are not forced to equal widths.
- **FR-017**: The library MUST allow each sub-box to declare which dimensions are expandable (both width and length by default, and height if explicitly enabled). Non-expandable dimensions stay at their minimum specified value.
- **FR-018**: The library MUST support non-rectangular box outlines derived from 2D polygon paths, allowing compartments and contents to be clipped to the polygonal interior boundary.
- **FR-019**: The library MUST apply configurable clearance gaps between nested boxes and between compartments to account for 3D printing tolerances. The library MUST apply 1-2mm of clearance slack in the X and Y directions around nested sub-boxes relative to the game box walls or adjacent boxes to allow them to be easily added to and removed from the game box.
- **FR-020**: The library MUST allow lids to be decorated with text labels that auto-size to fill the lid area minus a configurable border margin. If the computed text height is below a configurable threshold (default 4mm), the label MUST be skipped.
- **FR-021**: The library MUST support two label layout modes: framed (rectangular frame with diagonal hatching behind text for bed adhesion, plus a small outer border) and frameless (text only). Both modes SHALL support corner-to-corner diagonal text orientation. In framed mode the hatching is the **striped grid** FR-022 colours; the plate it is cut into stays the box's material.
- **FR-022**: The library MUST support three independently settable accent colors on lids: label text color, frame top layer color, and pattern top layer color. Each MUST have a default that produces a legible lid without being set (FR-000a).
  - **Label text defaults to black.** A label is read against the lid it is cut into, and the lids this library makes are printed in whatever the game's colour is — so the text needs the one colour that reads against all of them. White was the default and disappears on any pale box.
  - **The frame's striped grid defaults to light grey.** It is a texture behind the text, not a second label: it has to separate the lettering from the lid without competing with it, which a light neutral does and a saturated accent does not.
  - **What sits behind both is the box's own material**, not a third colour. The plate the text and the hatching stand on is simply lid — so it needs no colour, no insert and no material change, and the frame reads as part of the box rather than as a sticker on it.
- **FR-022a**: A lid's label MUST be **inset into** the lid, not raised on it: the recess is cut to a top-layer depth and filled flush, so what changes at the label is the **colour of the top layer** and nothing else.
- **FR-022b**: A coloured part MUST carry the colour it prints in **alongside** its geometry, not only baked into it. A geometry library's solid has no colour to read back — the attribute is the method that *sets* one — so a caller that asks a solid what colour it is gets a bound method, and code written to fall back when it cannot read one silently renders every part in its parent's colour. That is what a preview did to every lid label: the lettering was there, in exactly the colour of the lid it sat on.
  - The lid's top face MUST stay flat. Raised lettering is the first thing knocked off a lid that lives in a box with other boxes, it stops the lid sitting flush under whatever is stacked on it, and on a sliding lid it fouls the mouth of the channel.
  - Only the areas that print in a **different** colour may be recessed — the glyphs, and the frame's striped grid. The plate between them MUST be left uncut, which is what makes it the box's own material (FR-022) without an insert to place or a colour to choose.
  - This applies to the multi-material export. A single-colour export has no second material to inlay, so it keeps engraving the text (FR-036): there, depth is the only thing that can make a label visible at all.
- **FR-023**: The library MUST support through-hole surface patterns that cut completely through the lid, saving filament in non-structural areas.
  - **Every member of the pattern catalog MUST draw the shape it is named after**, and the catalog MUST contain only members the library can draw (FR-000g). The catalog was specified as a 47-member port of the original toolkit's `ShapeType` enum and shipped drawing three shapes: the fifteen pentagon tilings and the twenty tessellations wrapped an import of a package that is not in this repository, inside a bare `except`, and fell back to square holes — so a lid asking for LEAF got squares, and so did every one of Emberleaf's twenty-one lids.
  - The catalog is therefore what exists: **NONE**, **SQUARE**, **CIRCLE**, **HEX** and **DENSE_HEX** (hexagons in staggered rows), **TRIANGLE** and **DENSE_TRIANGLE** (alternating point-up and point-down), **OCTAGON**, **VORONOI**, **LEAF**, **LEAF_TESSELLATION** and **LEAF_VEINS**.
  - **LEAF** MUST draw leaves. Each is the pointed oval two overlapping circles leave, twice as long as it is wide — at 1:1 it is a circle, and it is the taper that reads as a leaf — with a **midrib** of lid left along its spine, which is what distinguishes a leaf from a pointed oval and braces the widest part of the hole. A leaf too narrow to keep a printable opening either side of the rib MUST be cut whole instead, because two slits read as a crack in the lid.
  - The leaves MUST **tessellate**: rows offset by half a pitch, stepped so that they interleave. Where one leaf is at its widest its neighbours above and below are near their tips, so the rows nest, and the step MUST be solved from the leaf's own outline rather than set to its width — stepping the full width leaves a band of solid lid along every row and the pattern reads as stripes rather than as foliage. The web MUST come out the same along a row as between rows.
  - **VORONOI** MUST draw Voronoi cells: one seed point per cell of a jittered grid, each cell the region closer to its own seed than to any other. Neighbouring cells therefore **share a straight edge**, which is the whole of what makes a Voronoi read as one. Round holes on a jittered grid MUST NOT be substituted — they leave a web that fattens and thins between every pair, and read as spots rather than as a net. Each cell MUST be inset by half the web, so the material left is the web and it is an even width; the corners, where three cells meet at a point, MUST be rounded, because a sharp junction in a thin lid is a stress raiser. The seed MUST be fixed, since the pattern is part of the exported geometry the fingerprint is taken over (SC-012).
  - A pattern whose cells **tile** MUST have its derived pitch floored higher than the generic one. The default pitch — an eighth of the area's shorter side — is calibrated for a hole *inscribed* in its cell, which is what most of the catalog cuts; where the cell **is** the hole, the same number leaves a cell only a few times the web, which prints and reads as a peppering of pinholes. Only the **derived** pitch is floored: a caller who asks for 5mm cells MUST get 5mm cells (FR-000g).
  - **LEAF_TESSELLATION** MUST draw a leaf that genuinely **tiles the plane** — a seven-sided tile whose edges pair up, so it meets its neighbours edge to edge with nothing left between them. This is a different pattern from LEAF, not a refinement of it: LEAF spaces pointed ovals out and solves for the gap, while this covers the area, so the material left over **is** the web and the lid shows a net of leaf outlines rather than a sheet with leaves punched out of it. The tile MUST be verified by area: one leaf's area equals one lattice cell's, which is the whole claim of a tessellation in one number.
  - **LEAF_VEINS** MUST be that same tiling with a **midrib and side veins** left as material inside each leaf. The veins MUST be simple — a midrib from base to tip and a few straight branches running forward from it to the tip-side margin — and every one MUST end on the midrib or on the leaf's outline, because a vein floating in the middle of a hole is an island the printer has nothing to build on. No vein may start at the leaf's **base**: three leaves meet there, so veins converging on it compound into a six-pointed star across the lattice and what the eye picks out is the star rather than the leaves. The reference pattern this is modelled on branches each vein twice more and rotates the sub-branches about the base; at a lid's scale that detail closes into a blur, and its strokes were placed by constants that only held at one leaf size.
  - A tiling pattern relies on the lid's **border** to hold it together. The material it leaves is a connected net, so every piece of it reaches the boundary of the patterned area and joins the border there; with no border, pieces of the net at the edge would be islands.
  - A member added to the enum without a fill MUST raise, not substitute another member's shape.
  - A pattern's cell size MUST default from the lid's own shorter side rather than a constant, so the same pattern reads the same on a token lid and a card lid (FR-000).
  - **A lid MUST keep one border**, solid all round, and the pattern and the label MUST both respect it. One number, not two: what a viewer sees is a single band of plain lid with things inside it, so a label measured from a different edge than the pattern reads as a mistake. It defaults to **8mm** and is settable.
  - The **label MUST sit inside that border by a further 2mm**. The border is a band of plain lid; a label level with its inner edge reads as touching the pattern rather than occupying a space of its own. So the text's margin is the border plus its own inset — 10mm from the lid's edge by default — while the pattern's is the border itself.
  - The border is what the lid is picked up and located by, and on a sliding lid it is what rides in the grooves, so it has to survive whatever is put on the face.
  - **The pattern MUST reach that border**, not merely stay inside it: the lattice runs past the edge of the area and is **clipped** to it, so a hole straddling the boundary comes out as a partial hole. Placing only whole holes leaves up to a cell's worth of unused margin inside the border — a lid asking for 8mm got 12mm or more of solid edge on two sides, and the pattern looked as though it had shrunk away from it.
  - **The lattice MUST start a full cell outside the area, on every side**, and MUST be **anchored on the area's centre** rather than grown from one edge. Both are needed and for different reasons. A staggered row is shifted half a pitch, so a lattice beginning at the area's own edge begins *inside* it on every other row and leaves a strip of material along the leading edge. And a lattice grown from an edge lands wherever the arithmetic puts it: on a 96 x 70 lid one side was cut through the hexes and the other through the webs between them, removing 56mm³ of material against 33mm³. Anchored at the centre with a cell of run-up, opposite edges are mirror images and every edge is cut alike.
  - Where a pattern meets a **frameless** label, the holes MUST stop at the **glyphs themselves**, with no margin around them by default. A stand-off puts a solid halo round every letter, so the text reads as letters on a plaque rather than as letters on the lid. It is not needed for support: the keep-out is the glyph outline, so every stroke keeps its own footprint of solid lid, and the label is inlaid into that lid rather than perched on it — the plastic goes all the way down. The margin MUST be settable, for a lid whose pattern is coarse enough that a stroke would otherwise finish on the very edge of a hole.
  - A pattern MUST be **moved** into the area, never re-anchored to it by its bounding box. Re-anchoring discards the centring above and pushes the whole overhang to one side, which is what produced that asymmetry.
  - **A hexagonal pattern MUST tile as a honeycomb**: every neighbour, in the row and in the rows either side, exactly one pitch away, with alternate rows offset half a pitch. That requires the hexagon's flats to face along the row — the lattice and the hexagon have to agree about which way is across-flats, and tiling one orientation with the other's spacing is not a honeycomb, it is rows of hexagons that clear each other by accident.
  - The scatter in VORONOI MUST be **deterministic**: the pattern is part of the exported geometry and is covered by the export fingerprint (FR-031), so a fresh random layout each run would rewrite the file forever.
- **FR-024**: The library MUST support patterns with multiple colors, where different pattern elements can be assigned different accent colors.
- **FR-025**: The library MUST support multi-material (MMU) printing: positive inserts printed in a different colour/material from the box body.
- **FR-026**: The library MUST expose a fluent builder API so users chain calls to define a box.
- **FR-027**: The library MUST report dimensioned requirements for the 3D printer bed: the bounding box of each generated piece.
- **FR-028**: [DEFERRED] The library MUST allow boxes to be split/sliced for printing on smaller beds by dividing parts along user-specified cut planes. Deferred to future release — not in v1 scope.
- **FR-029**: The library MUST export each box body and each lid as separate 3MF files containing all material/color assignments (multi-color 3MF), and also export single-color 3MF variants for single-extruder printers.
- **FR-030**: The library MUST export a BoxKit by producing 3MF files for the outer box (body + lid), every nested sub-box (body + lid), and every spacer tray (one file each) -- all in both multi-color and single-color variants.
- **FR-031**: The library MUST decide whether to rewrite an exported file from the **description the piece was built from**, not from its mesh. A digest over everything that shapes the piece — the box's fields, its compartments, its lid, the project's thicknesses and rounding, and the curve precision — is recorded beside the file and compared on the next run; an unchanged description MUST NOT rewrite.
  - Comparing the exported meshes instead measures the wrong thing. The geometry engine does not promise to retriangulate a complex CSG tree identically between runs, so a mesh comparison reports "changed" for a description nobody touched — measured on the Emberleaf insert, nine of its pieces were rewritten on **every** export, which is SC-012 failing on exactly the parts that are most expensive to rebuild.
  - No tolerance fixes that. One loose enough to absorb a retriangulation sits far above the 0.1mm the library promises to resolve (FR-003), so it would also absorb real changes.
  - The digest MUST cover the curve precision, since the same box built at draft and at print precision is different geometry (FR-046).
  - A missing or unreadable record MUST be read as a miss — the file is rewritten once and then settles — never as an error.
  - The digest MUST cover the **contents** of any file a box's geometry is cut from, such as an SVG silhouette, not merely the path to it. Named by path alone, editing the drawing changed nothing about the description and the well was never re-cut.
  - The digest MUST **not** cover where the piece sits in the game box, nor the other half of the box: a 3MF holds its piece in its own frame, so moving a box cannot change the file, and a body does not change when its lid's label does. Including either rebuilds parts whose geometry is identical — shortening one box in a stack rebuilt every box above it.
- **FR-031a**: A piece whose file is current MUST NOT be **built**. The digest is knowable before any geometry is cut, so an unchanged box costs nothing rather than being built and then discarded. Building first and deciding afterwards is what made a repeat export cost the same as the first one — at the 256 facets an export uses (FR-046), tens of seconds to minutes for a result that is thrown away.
- **FR-031b**: The library MUST provide a **manually triggered** command that produces the print-quality files, and nothing else may produce them as a side effect. An export at print precision is far too slow to happen behind a preview.
  - It MUST accept a subset — one insert, or one box within one — so a change to a single box can be exported without rebuilding its neighbours.
  - It MUST accept a way to rebuild everything regardless, for the case where the recorded state is not trusted.
  - A partial export MUST NOT delete or rewrite the pieces it was not asked for: it knows nothing about them, so it cannot conclude they are stale.
- **FR-032**: The library MUST report which files were written and which were skipped during export, so the user knows what changed.
- **FR-033**: The library MUST generate a valid PDF packing guide — a standards-compliant PDF file that renders correctly in any PDF viewer — showing the box layout in a 3D isometric/oblique angle projection. The PDF MUST contain multiple pages representing the box layout broken down layer-by-layer (e.g., base layer, middle stacks, top boards). Each page MUST render only the boxes and spacers belonging to that specific layer in full color (with visible, readable labels and index numbers), while rendering the already-packed lower-layer boxes in light gray as background context to clearly show where they sit.
- **FR-034**: The library MUST cache the PDF output — regenerating only when the box layout or library version has changed since the last export (same SHA-256 hash gate as 3MF files).
- **FR-035**: The library MUST allow MMU (multi-color) and single-color exports to use different label specifications per box. For example, a lid can use a frameless label for MMU printing (text only, no frame) and a framed label for single-color printing (frame + text cutout).
- **FR-036**: For single-color export, compartment labels MUST render as single-layer cutouts engraved into the compartment floor (0.2mm deep) so they are visible as recessed text without a second material. For MMU export, compartment labels MUST render as raised text in a second color extruded 0.2mm above the floor.
- **FR-037**: The library MUST support standalone boxes — boxes generated independently without any enclosing game box. A standalone box is a single `BoxSpec` built and exported directly, with no nesting layout, no auto-sizing, and no packing phase applied.
- **FR-038**: The library MUST support stackable boxes for no-lid box types. A stackable box has an interlocking ring (a recess on the top rim and a matching ridge on the bottom, or vice versa) so multiple boxes stack securely without sliding. Stacking MUST support both inside-fit (ring nests inside the box below) and outside-fit (ring fits around the box below) modes, selectable per box.
- **FR-039**: The library MUST support magnets embedded in box side walls, with two slot types: round magnets (cylindrical cavity, e.g., 6mm diameter × 3mm depth) and rectangular magnets (box cavity, e.g., 10mm × 5mm × 2mm). Magnet count, position, and slot dimensions MUST be configurable per box. Magnet slots MUST be placed on opposing sides so stacked boxes attract correctly.
- **FR-039a**: Magnet slots MUST go in the pair of opposing walls that carries **no finger hole**. On a no-lid tray FR-047 puts the holes in the longer pair, so the magnets go in the **shorter** pair; both pairs are opposing, so nothing about the attraction changes. Left on one fixed pair they collide: a magnet pocket is cut at the middle of a wall at mid-height, which is inside the finger cut whenever the two land on the same wall, and the result is a tray with a hole where a magnet should be and no way to see it in the geometry. Where the user has placed holes explicitly on both pairs, FR-006c reports the collision rather than the library guessing.
- **FR-040**: The library MUST support hex-grid compartments for storing hexagonal tiles. A hex-grid compartment is a rectangular region subdivided into a `rows × cols` array of hexagonal cutouts, each sized to hold one hexagonal tile. The layout MUST be computed from `tile_width` (the apothem-to-apothem width of the tile), deriving the hex circumradius as `tile_width / 2 / cos(30°)`, with configurable `spacing` between cells and `rows`/`cols` counts.
- **FR-041**: Each hexagonal cutout in a hex-grid compartment MUST support a raised central pillar (a "push block") — a smaller hexagonal post protruding from the floor in the middle of the cell — so that a seated hex tile rests on the pillar rather than flat on the floor, making it easy to grasp and remove. The pillar height MUST be configurable via `push_block_height` (default 0 = no pillar); when `push_block_height` is 0, the hex sits flat on the cell floor.
- **FR-042**: Each hexagonal cutout in a hex-grid compartment MUST support a finger hole in the cell floor (a circular cutout through the floor at the cell center or offset to one edge) so a finger can push the hex tile up from underneath. The finger-hole diameter MUST be configurable; the finger hole and the raised pillar MUST NOT occupy the same space — when both are enabled, the finger hole is offset from the pillar.
- **FR-043**: All compartments, finger holes, and finger scoops MUST be smooth with continuous, rounded transitions — no sharp 90° edges or corners. This applies to: the bottom edges of a compartment well (where the wall meets the floor), the top rim of a compartment, the entire profile of a finger scoop/notch (top opening curving into the wall and bottom blending into the floor), and the walls of a finger hole. Every exposed edge a finger or a game piece would touch MUST be filleted/chamfered so nothing snags.
- **FR-043d**: Every **exposed edge of every printed piece** MUST be rounded over: the four vertical corners, the bottom edges, and the top edges of the assembled box. Where the top rim of a body is a mating surface for a lid, the rim itself MUST stay square (a rounded sealing face does not seal) and the corresponding rounding MUST be carried by the lid, so the **closed** box still presents rounded top, sides and bottom. Rounding MUST NOT trim features that legitimately extend beyond the declared envelope, such as a hinge barrel.
- **FR-043f**: A **lidless box's rim MUST be rounded on both sides** by `wall_thickness / 2` — the outer top edge and, when the box is hollow, the inner top edge too. An open tray's rim is exposed on both faces and is the edge a hand actually runs along when lifting it. This does **not** apply to a lidded box, whose rim is a sealing surface and whose rounding lives on the lid.
- **FR-043f1**: A **sliding-lid box's top edge MUST be rounded**, by a **quarter** of the wall. It is the exception to FR-043d's rule that a lidded box keeps its rim square: that rule holds because the lid seals against the rim and carries the rounding itself, and a sliding lid does neither — it lies down in the channel, so what stands at the top of the closed box is the rails' own outer edges, which a hand runs along whenever the box is picked up. A quarter rather than the usual half because the rail is what is left of the wall once the groove is cut into it, and half a wall off its top edge is most of the bearing the lid rides on.

**The outline**

- **FR-050**: An **edge scoop**'s outline, read from the top down, MUST be: the flat top surface, a **mouth roll** that leaves the top face *horizontally* and arrives at the throat *vertically*, a straight **throat**, a **floor fillet** from the throat into the flat bottom, and the **flat bottom**. Every join MUST be tangent, so the outline is smooth without a fitted blend.
- **FR-051**: Exactly **four numbers** define that outline, and the requirements MUST name them consistently:
  | Name | What it sets | Default | Settable |
  |---|---|---|---|
  | **width** (twice the throat radius) | how wide the cut is — how much finger goes in | 28mm (a fingertip) | per cut |
  | **corner radius** (`r2`) | how the base curves into the sides | half the width on an exterior hole; `0.65 ×` the half-width on a compartment scoop, which keeps its flat run | per cut |
  | **mouth flare** (`r1`, `rounding_radius`) | how far the roll reaches *outward* at the rim — the mouth's extra width | half the throat radius (FR-059) | per cut |
  | **roll rise** | how far the roll reaches *down* — how gently the top surface turns into the wall | 1.6 × the mouth flare (FR-057) | per cut |
  | **floor fillet** (`r2`, `bottom_rounding`) | the blend from the throat into the flat bottom | derived from the throat radius (FR-077) | per cut |
  The roll is therefore an **ellipse quadrant**, not a circular arc: flare and rise answer different questions and MUST NOT be tied together (FR-057). Calling the pair "two radii" is what let the rise become an unreachable constant; every one of the four MUST be reachable from the API.
  - The mouth roll MUST be tangent to the **surface it opens onto** — the top of the wall it is cut into (FR-067), which on a lidded box is not the box's own rim (FR-064). A transition that arrives vertical there leaves a hard edge where the flat top meets the cut, which is the crease this requirement exists to remove.
  - The bottom MUST be flat with a floor fillet, not a semicircular trough: a piece sits on a flat floor and is lifted off it, and the fillet is what lets a finger get under the piece.
  - A **flat run MUST survive at the base of a compartment scoop** whatever floor fillet is asked for: it is capped so at least a quarter of each half-width stays straight, because a piece rests on that run and a fillet grown to the full half-width closes it into a trough. The rule is about what the cut *holds*, so it does **not** apply to a cut nothing rests in — a box's exterior finger hole is a grip, and its base is round (FR-054).
- **FR-052**: A grip's outline MUST be built as **two circles joined by their internal tangent**: a base circle sitting on the bottom of the cut, the mouth's roll circle at each end, and a straight run between them that touches both. This is one construction for every proportion, and the shapes that were being reached for separately fall out of it — on a deep cut the tangent run comes out vertical and the result is the familiar round base with straight sides; on a shallow one the same base circle presents a long flat sweep and the run carries it up and out to the roll. Nothing switches; only the numbers change.
  - The tangent MUST be the **internal** one — the run crosses between the circles, touching the base circle on its outer side and the roll on its inner side, because the two arcs curve opposite ways. The external tangent is the natural first thing a solver returns and it is wrong here: it wraps both circles the same way and throws the flank wide of the cut.
  - The two circles MUST stay **apart**. Sized until they touch, the run collapses to a point: the outline is still continuous and still tangent, and it reads as a single wobbling curve with no flank at all. The touching radius — `(A² + u² - flare²) / (2 × (u + flare))`, with `A` the mouth's half-width and `u` the depth less the roll's rise — is therefore a **cap** on the base circle, never its size.
  - The base circle **grows as the cut gets shallower**: its radius is the larger of half the cut's width and **nine tenths of the touching cap**, and it sits centred, tangent to the bottom of the cut. Half the width alone is right only while the cut is deep enough to hold that circle; below that it leaves the base covering barely half the width with a long straight ramp either side, which reads as a shallow trapezoid rather than a dip — the base has to take more of the cut, not less, as the depth falls away. Measured at a 40mm-wide cut: at 30mm deep the base covers the full half-width and the rule changes nothing, at 10mm deep it covers three quarters instead of a half.
  - Nine tenths, because the last tenth is the flank. The cap is where the circles touch and the flank vanishes; approaching it, the base takes as much of the cut as it can while leaving a run to see. This is a proportion of the geometry rather than a length, so it holds at every size of cut.
  - A grip's roll MUST be a circle **tangent to the top face**, so its radius and its rise are **one number**. Where the cut is too shallow to hold the radius asked for, that radius MUST shrink — not merely its rise. Clamping the rise alone lifts the circle's centre without shrinking the circle, so it stops touching the top face (it pokes above the rim) and stops being the circle the flank was solved against: the tangent is then computed for one circle and drawn against another, and the outline runs **sideways** — backwards in x, downwards in y — to reach it. That is a cut with a step in its shoulder, and it appears only on cuts shallow enough for the clamp to bite, which is why it survived.
  - A grip's roll MUST be **circular** (its rise equal to its flare). The tangent construction is exact between two circles and only approximate against an ellipse, and this is the one place where exactness is the whole point. FR-057's independent rise applies to a compartment scoop, whose flank is a vertical run rather than a tangent; a grip's gentleness is set by the roll's own radius, which is settable.
- **FR-053**: The straight run between a scoop's r1 and r2 arcs MUST be the two circles' **common tangent**, solved rather than assumed. Both joins are then tangent by construction, whatever the two radii are and wherever the circles sit; assuming the run is vertical is correct only for one particular placement and fails silently — as a step in the scoop's wall — for any other.
- **FR-054**: A cut's **corner radius MUST be kept, and the outline fitted around it by tangents** — not shrunk until it fits. The corner circles and the mouth's roll are joined by their common tangent (FR-053), so a large radius does not need a wide cut to live in: what gives is the straight run between the circles, which is exactly what solving the tangent does. Shrinking the radius instead is the failure this exists to stop, and it compounds — a cap to leave a flat run, then a proportional scale to fit the height, and what a caller asked 20mm for comes back 14.4mm with nothing in the geometry to say it was ever refused.
  - Where the height genuinely cannot hold the circle, the **roll's rise gives first** (FR-057 — it is the gentleness of the mouth, and the one quantity that can be spent), down to a circular roll and no further. Only then does the radius reduce, and only to what remains.
  - An exterior finger hole's corner radius therefore **defaults to half the cut's width**: the largest circle there is, which makes the base a single round curve running into the tangents rather than a flat pan with two corners. What the depth allows of that is what it gets.
- **FR-055**: A cut's **width and its corner radius MUST be settable independently**. They answer different questions — how much finger goes in, and how the base curves — and tying them (a radius derived only as a share of the width) makes a wider grip the only route to a rounder base. Both MUST be settable per cut, and either alone MUST change the outline without changing the other.
- **FR-056**: A grip MUST NOT be **wider than it is deep**. The angle its flank arrives at the rim is set by that aspect and by nothing else: at 45mm wide over 9mm deep the sides can only come in at about 34°, against about 70° on a cut of the same width at 19mm deep, and the two stop reading as the same feature — the shallow one meets the top face at a slant where the deep one rolls into it. A shallow box therefore gets a **smaller** grip, not a stretched one; the finger still goes in, and the shape is the one the rest of the library uses.
  - The width is a **maximum, not a promise**, in the same way the wall's span already caps it: a cut asked for a width its depth cannot carry is narrowed, not refused.
  - Note what this does and does not achieve. It brings the flank from about 34° to about 45–56° against the deep cut's 70–76° — much closer, not identical, because the mouth's roll is a fixed 3mm (FR-047) and a fixed radius on a smaller cut is proportionally larger. True similarity would need the roll to scale with the cut too, which would leave a small grip with a lip too small to feel. This requirement chooses the family resemblance over the proportion.
- **FR-057**: The scoop's own radii MUST be sized so the **width of the cut and the gentleness of its curve are independent**. The top roll's outward flare sets the mouth width; its downward rise sets how gently the top surface turns into the wall. Tying them together (a circular roll) means the only way to get a gentler curve is a wider cut, which is backwards on a shallow wall — there is height to spare for the curve but no width to spare for the mouth.
- **FR-058**: Where a scoop's throat and its `r1` roll cannot both fit the available span, they MUST be reduced **together**. Capping the throat first and giving `r1` what remains sets `r1` to exactly zero on any cut already at half the span, silently deleting the most visible part of the scoop.
- **FR-059**: Scoop and finger-hole geometry MUST be usable **without overrides**. Every radius MUST have a default derived from the cut itself rather than a fixed constant: `r1` from the throat width, `r2` from the throat width, the cut's height from its radius, and the face fillet from the wall thickness. A fixed constant is invisible on a large cut and overwhelming on a small one, and a default that needs tuning per box is not a default.

**Which cut**

- **FR-060**: A well holding a **stack of cards** MUST be emptied by a hole **through the floor**, not by a scoop. A scoop lets a finger down the side of the stack; a stack that fills its well has no side to reach down, so what actually lifts it is a thumb from underneath. The original toolkit's card boxes all do this (`FingerHoleBase`, translated a floor thickness *below* the base so the bore goes right through), and the port had been giving them scoops.
  - The cut is a **circle through the floor at the wall** the cut's side names, centred on that wall and straddling it so it breaks through — the finger arrives under the edge of the stack, where a card is lifted from, and the middle of the floor is left intact.
  - Its top MUST be rolled into the wall's rim, and its **outside** face rolled where it emerges — and only that face. The inside is what the stack rests against, where a fillet is a gap the bottom card slides into rather than anything a hand touches; the **base stays flat**, because it is a surface the box sits on, and a fillet there leaves a curled lip around the hole.
  - Through the wall the cut MUST hold **one section**, square at the inner face and rolled only at the outer one. A cut that changes width inside the wall leaves a ridge running round it — and that ridge, not the rounding, is what a hand and a card meet.
  - Below the well's floor the cut MUST be the bore and the wall's own thickness and **nothing more**. Whatever is done inside the wall to keep its section constant stops at the floor: carried on down, it scallops the base *inside* the well across the whole width of the cut, and the base is the surface the box stands on.
  - Being flat at the base is a *placement* rule as much as a rounding one: the cut has to start far enough below the box for its face fillet to finish outside the material. A cut ending a hair under the floor puts that fillet's roll back up inside the base.
  - A **scoop MUST remain available** per compartment, because a well that does not hold a stack — loose tokens, a bag, a board — wants a side dip and not a hole in its base.
- **FR-061**: The choice between a wall notch and a floor bore MUST be made at a depth a **card well clears**. The two answer different situations — a notch is a dip a finger hooks into and needs depth to be one; a bore is a bowl in the well's own floor, for a tray too shallow for that — and the boundary was inherited at 8mm, which is above the 6.5mm well of a card box that plainly wants the notch. At 8mm such a box came out with a nick in its rim about a millimetre deep and the wall whole underneath, which is not a grip at all. The boundary MUST sit below a card well and above the shallow tray the bore is for: **5mm**.
- **FR-062**: A **floor finger hole** is a different cutout from an edge scoop and MUST NOT share its profile. It is a bore a piece is pushed *up* through, so its bottom is a bowl tangent to the floor rather than a flat pan; it carries the same r1 roll at its rim.
- **FR-063**: A scoop's bore MUST be tangent to the compartment floor, so the bottom of the scoop curves into the floor rather than meeting it at a corner.

**Where it goes**

- **FR-064**: An exterior finger hole MUST hang from the top of the box's **interior**, not from its outer rim. On a lidded box the lid or its track occupies the band above the interior, so a hole aligned to the rim begins inside solid material and reads as a nick in the top edge. Box types whose body is already shortened for their lid (cap, slipover) MUST declare their own interior top so the allowance is not applied twice.
- **FR-065**: On a box where that interior top is **below the rim** — anything with a lid band — the cut's **whole mouth roll MUST finish below it**. The interior top is a plane inside material, not a face, so a roll aligned to it has nothing to be tangent to; the cut MUST therefore be built shorter by whatever the roll needs, rather than run to full depth and be sliced off at that plane. A horizontal slice through the roll is the square edge FR-043 forbids, in the one place a finger actually reaches. On a lidless box the interior top *is* the rim and the roll finishes tangent to it, as FR-050 requires.
- **FR-066**: Exterior finger holes MUST work on **every box type in the registry whose body is hollow** — at the time of writing: no-lid, path, sliding, sliding-catch, card-library, cap, cap-path, slipover, slipover-path, inset, hinge, filament-hinge and magnetic — and MUST land at the same place relative to the interior on each. A type that cannot carry one MUST say so by declaring it, not by producing a cut in the wrong place.
- **FR-067**: A **compartment** finger scoop MUST run from the compartment floor to the top of the **wall it is cut into**, so its r1 roll merges into that wall's top surface. Stopping at the interior ceiling leaves the lid band standing above the cut as a step, and buries the roll inside the wall where it can be neither seen nor felt.
- **FR-068**: A finger scoop MUST default to the **shorter** wall of its compartment. A card stack is lifted out across its narrow dimension, so the cut belongs in the short face; in the long face the user is reaching across the whole box to get at the cards. The side MUST remain overridable per compartment.
- **FR-069**: On a **sliding-lid box** (and any card box using one) the finger scoop MUST be in the wall the **lid slides out of**, and MUST NOT cut into the lid's grooves. The other three walls carry the lid — two of them hold the grooves it rides in — so a scoop cut there removes the bearing that keeps the lid straight. This overrides the shorter-wall default below.
- **FR-070**: The library MUST model each wall's top height **per side**. The four walls of a box need not end level — a sliding box's exit wall stops a lid thickness below the others, because that is where its channel runs out through it — and anything aligning to "the top" (a scoop's roll, a cut's trim, a hole's placement) MUST ask for the side it is on. A single box-wide top is wrong for any type whose lid interrupts one wall, and fails silently: the feature is simply built at the wrong height.
- **FR-071**: Each box type MUST be able to declare its own per-side tops, with a default of the box's top face less any band its lid occupies. Types that shorten their whole body (cap, slipover) or interrupt one wall (the sliding family) declare accordingly.
- **FR-072**: The cut's dip below the well floor MUST stay a small constant (0.2mm) whatever the floor thickness. It exists only to keep the cut's bottom face off the floor plane; sized as a share of the floor it consumes half of a 2mm floor and shows as the cut eating into it. The dip is **not** room for the face fillet to finish in — that is what FR-075's taper is for — and MUST NOT be enlarged to make one fit.

**Where it emerges**

- **FR-073**: Where a scoop or finger hole emerges on a face of a wall, the cut MUST be filleted onto that face so it flows onto the side of the box instead of ending in a sharp edge. Each face MUST be independently switchable, since an outward-facing wall wants the softening more than an internal divider does.
- **FR-074**: An edge scoop's **flat bottom MUST NOT meet the wall's faces at a square edge**. The cut's bottom is a horizontal plane through the wall, and where it emerges it needs the same face treatment as the rest of the outline, so what a finger meets at the base of the scoop is a rolled edge rather than the wall's sawn cross-section.
- **FR-075**: The face fillet MUST **taper to zero as it approaches the flat bottom**, so it finishes inside the cut's own height. A fillet of constant radius reaches a radius *below* the outline — the flare is isotropic in the profile plane — and there are only two other ways to absorb that, both of which cost more than the taper: clipping it at the floor slices the fillet mid-curve and leaves the sawn edge FR-074 exists to remove, and raising the flat bottom by a fillet's radius takes that much depth off every compartment scoop in the library. The taper keeps the floor thickness (FR-072), the depth (FR-006b) and the rolled base, and it is the only one of the three that does.
- **FR-076**: Where a cut has **wall below it rather than floor** — a box's exterior finger hole — the fillet MAY instead be allowed to finish below the outline, since there is material for it to finish into and no floor to protect. The cut's reach is then measured to the fillet's deepest point, as FR-006b requires.
- **FR-077**: A finger scoop's **two curves MUST be sized from different quantities**: the top roll from the **rounding radius** (how far the mouth flares out at the rim) and the bottom fillet from the **throat radius** (how wide the cut is). Driving both from the rounding radius makes the U symmetric about nothing in particular — the floor fillet grows and shrinks with the mouth's flare instead of with the cut it has to blend into, and on a wide shallow scoop it swallows the flat bottom entirely.

**Pull-outs**

- **FR-078**: Every **slot cut to a piece's silhouette** MUST carry a finger **pull-out**: a dish across the slot letting the piece be lifted out. Cutting a slot to a piece's outline is what makes it hold the piece — and what leaves nowhere to get a fingertip — so the pull-out is part of the slot, not an extra. It MUST default to **half the piece's depth**: deep enough to get under the piece, shallow enough that the piece still seats flat rather than tipping into the dish. Its depth and width MUST be settable per slot, and a slot MUST be able to decline one.
- **FR-079**: A pull-out MUST be **curved in from the surrounding floor** on every edge, so a finger slides down into it. A dish with a square step around it is harder to use than no dish, because the step is what a fingernail catches on.

- **FR-044**: The rounding/smoothing radius MAY be small — a 1mm fillet (or similar small radius) is an acceptable default; it is not required to be large. The default radius for a box's exposed edges and its internal wall/floor junction is **`wall_thickness / 2`**, the largest fillet a wall can carry while keeping half its thickness as flat face. The rounding radius MUST be configurable per project and per box (a `rounding` parameter), with `0` leaving edges square. Box types that do not support configurable corner rounding MAY apply a fixed small radius.
- **FR-044a**: Rounding MUST NOT be applied where it would break a fit. In particular, fillets on a box's **internal vertical corners** MUST NOT intrude into the band where a lid seats or slides — such a fillet runs the full height of the box and adds material exactly where a sliding plate has to pass.
- **FR-044b**: Where a **partial lid** grips the body — a cap's skirt over the body's stepped band, a slipover sleeve over the whole body — both halves of the grip MUST be rounded to the **same, smaller radius** (default: half the outer radius), so the lid's inner corners nest over the body's rather than meeting them at a gap. The radius is smaller because the mating surface is a fit rather than a finish, and because a skirt wall is only half a wall thick: a full-size fillet would consume most of it. The radius MUST be configurable (an `inner_rounding` parameter, per project and per box), with `0` leaving the grip square.
- **FR-044c**: The **inside of the box** — the interior cavity that holds the contents — keeps square vertical edges. Only the wall/floor junction is filleted (FR-043).
- **FR-044d**: Rounding MUST round **all four** vertical corners, not a subset. (Stated because it is a real failure mode rather than a truism: an edge selector naming the Z *axis* resolves to a single edge, and a box so rounded looks correct everywhere except three of its corners.)
- **FR-044e**: A fillet on a cut MUST be a **roundover of the surrounding face**, not a cove gouged into it. The blend MUST be tangent to the face it emerges on, so the face rolls into the cut; a blend tangent instead to the cut's own wall meets the face at 90° and hollows the inside of the wall while leaving the opening at nominal size, which is a cutout rather than a smoothing. The test that distinguishes them is measurable: **the cut MUST be wider at the face than it is mid-wall.**
- **FR-044e1**: A cut's face fillet MUST **follow the cut's outline** all the way round it. A fillet that shortcuts across a concave part of the outline — bridging a U-shaped scoop from one side to the other — is not a fillet on that cut; it is a ramp over its opening. Any construction that convexifies the outline (a hull between offset sections, for instance) violates this.
- **FR-044f**: Compartment rounding MUST be **0 by default** and opt-in per compartment. A well is only rounded when it is declared to hold loose pieces that have to be picked out; every other well — card slots, silhouettes, board recesses, anything shaped by its contents — stays square, because softening those changes a fit rather than improving it.
- **FR-044f1**: A well that IS declared a piece tray MUST have **both its vertical corners and its floor edges** rounded — corners alone leave the piece sitting in a square trough and defeat the purpose. The default radius is **the well's own depth × 2/3**, capped so it cannot exceed the well's footprint or depth. Sizing it from the cutout rather than from the box is deliberate: what makes a piece easy to retrieve is the curve the finger follows, so a deep well needs a large sweep and a shallow token tray a small one.
- **FR-044g**: An SVG silhouette or element pack MUST stay square **even when declared a piece tray** — its outline is reproduced exactly as authored (FR-045), and that overrides the tray default rather than combining with it.
- **FR-044h**: A lid's top and outer edges MUST be rounded **when they are on the outside of the closed box**, and only then. The radius MUST be capped so the lid keeps its support: no more than **half the lid's thickness**, since the edges of a thin plate are what hold and locate it, and a radius sized off the wall can consume most of one.
- **FR-044i**: A **sliding** lid MUST be rounded only on the edge that ends up outside the box — the end it slides out through, its top edge and the two vertical corners there. The edges that ride in the grooves, and the end that seats against the stop, MUST stay square: rounding them rounds away the surfaces that support and locate the lid.
- **FR-045**: SVG silhouettes and piece shapes (animal outlines, token cutouts, engraved shapes, etc.) MUST be reproduced faithfully — their outline is always kept fixed, even when the resulting geometry is hard to print (thin features, overhangs, sharp corners). Smoothing/rounding MUST NOT distort the piece silhouette; it applies only to the edges/corners that are not part of the piece's defining shape.
- **FR-046**: Curve precision MUST differ between a final export and an interactive preview. `export()` MUST default to a **high** facet count (256) because that geometry is what gets printed; `show()` MUST default to **no fixed facet count**, deferring to `fa`/`fs` so facets are sized by how large each curve actually is and the preview stays responsive. Both MUST accept an explicit override.
- **FR-046a**: Print-quality export is for producing the final 3MF files **only**. A CI pass MUST NOT produce printable output and MUST run at a draft facet count: what CI verifies about export is which files are written, skipped, cached and deleted, and none of that depends on how finely a curve is tessellated. The draft setting MUST be an external override (an environment variable), not a change to the library's default, so the shipped behaviour is unaffected.
- **FR-046d**: The **preview** MUST be able to show a subset — one named box, and its lid with or without its body. A box being worked on is looked at far more often than a whole insert, and on a twenty-box insert the whole thing is both slower and harder to see. Showing one box MUST build only that box.
- **FR-046b**: CI's geometry coverage MUST come from the **preview build path** (`preview_pieces()`, what `show()` renders) rather than from export: it resolves the layout, packs it and builds every body, lid and spacer without writing a file, needing a render binary, or paying print precision. Every example project MUST build this way on every CI run.
- **FR-046c**: `show()` and `export()` MUST build from **one** function. It resolves the layout and builds every body, lid and spacer; the preview renders what it returns and the export writes what it returns, and that is the entire difference between them.
  - This is a structural requirement, not a convention, because the convention was tried. Export assembled its own description and ran its own sizing pass — a near-copy of the preview's — and the two drifted: the exported description was missing its rounding, its `rim_free`, its `inner_rounding` and its per-side wall tops, and the export never rounded the lid or gave the compartment carve its top, its scoop side or its interior mask. FR-043f, FR-044b, FR-044h, FR-044i, FR-067, FR-069, FR-070, FR-071 and FR-002s were all absent from every printed part while every one of them passed its tests, because FR-046b routes the geometry tests through the preview.
  - Nothing outside that function may build geometry. A new output consumes the pieces it returns; if the pieces do not carry what a new output needs, the fix is to add it to the piece.
  - Per-colour-mode decoration (FR-036) is applied after the build, from one function both callers use, and a preview MUST show it — a previewed lid carries the label it will print.
- **FR-047**: A **no-lid box** MUST cut a finger hole into each of the **two walls whose span is its longer horizontal dimension**, so an open tray can be lifted from either end. "Longer" is read on the box's outer footprint, and a square footprint takes the pair spanning the length. The cut is the library's ordinary edge scoop (FR-050), not a second geometry. Each hole MUST be sized:
  - **Throat radius** = `min(20, min(length, width) / 4, height - floor_thickness + 1)` — a fingertip, capped at 20mm and at a quarter of the smaller **outer** footprint dimension. The `+ 1` is a tolerance carried from the original `no_lid.scad`; it cannot deepen the cut, because the reach below bounds that independently.
  - **Reach** = `min(throat radius, height / 2, height - floor_thickness - 5)` — the cut drops from the rim by a fingertip's radius, never past **half the box's height**, and **stops 5mm above the tray's floor**. The half-height cap is what keeps a tray a tray: a cut deeper than that leaves the wall it is cut into as two posts and a bridge, and on a shallow tray the fingertip radius alone would take nearly the whole wall. That strip is the whole of what carries the tray when it is lifted by the cut, and a wall thickness and a millimetre of it — which is what this rule used to leave — is a 3mm ribbon on a 2mm-walled box: enough to print, not enough to trust. Read the term that way round: it is a structural rule about what must survive below the cut, not an arithmetic accident.
  - A tray with no room for both that strip and a **2mm** cut gets no automatic holes at all (FR-047a), rather than a token dip bought out of the strip.
  - **Mouth flare** = 3mm.
- **FR-047a**: A wall too short for the hole's mouth MUST be **left uncut**, and "too short" MUST be read as leaving too little wall, not as failing to fit. The mouth is `throat radius + mouth flare` wide on each side of centre, measured against that wall's **interior** span (`span - 2 × wall_thickness`), and it may take at most **three quarters** of that span: where `2 × (throat radius + mouth flare) > 0.75 × span` the tray ships with no automatic holes. A mouth allowed the full span leaves two corner posts carrying the rim — a slot, not a grip — and one wider still breaks through into the adjoining walls. This is the one exception to FR-047's MUST, and it is silent by design: a small tray is liftable without a grip, and a broken corner is not.
- **FR-047b**: The automatic holes MUST be **opt-out**: a box that names any exterior finger hole of its own gets only the holes it named, and a box that asks for none gets none. A default that cannot be declined is a constraint, not a default (FR-000b).
- **FR-047c**: Automatic holes apply to a **rectangular** footprint. A path box whose outline is a polygon MUST get none: its walls are not the four the rule names, and there is no meaningful "longer side" to place them on. Such a box MAY still be given holes explicitly.

- **BoxSpec**: The complete configuration of a single box -- outer dimensions (explicit or auto-computed from compartments), wall/floor/lid thicknesses, lid type, compartments, finger holes, labelling decorations, material colours, print positioning, auto-expand behaviour (expandable axes), and a `no_rotate` flag (default `False`) that prevents the 3D packer from rotating the box. Immutable once built. If `size` is omitted, dimensions are derived from compartment layout during packing.
- **BoxType**: Abstracts the lid mechanism -- defines how the body is constructed (e.g., with dovetail grooves for sliding, with overhangs for caps) and what lid geometry mates with it.
- **Compartment**: A single well inside a box interior, defined by its 2D footprint (width x length, or a polygon path), depth, rounding radius, and optional finger cutout specification. Can emit both a negative cavity and a positive insert.
- **Compartment Group**: A collection of compartments that must stay together during layout, with a packing algorithm directive.
- **Lid**: The closure for a box. Includes a decoration specification with: label text (auto-sized, with framed or frameless mode and optional corner-to-corner diagonal orientation), through-hole surface pattern (any of the `PatternType` catalog, per FR-023), fingernail lift cutout, and three independently settable accent colors (text color, frame top color, pattern top color). Minimum text height threshold (default 4mm) suppresses labels that would print illegibly. Supports per-export-mode label overrides: MMU and single-color exports can use different label specifications (e.g., frameless for MMU, framed for single) via `mmu_label` and `single_label` sub-configurations.
- **PatternType**: The enum of lid surface patterns — **every one of which the library draws** (FR-023). NONE, SQUARE, CIRCLE, HEX, DENSE_HEX, TRIANGLE, DENSE_TRIANGLE, OCTAGON, VORONOI, LEAF, LEAF_TESSELLATION and LEAF_VEINS. It was specified as a 47-member port of the original toolkit's `ShapeType` enum plus the tessellation families, of which three were drawn; the rest fell back to square holes. A member is added here when the geometry to draw it is (FR-000c), so the list grows by implementation rather than by aspiration.
- **Finger Cutout**: A scoop or notch at a specific location on a box wall or compartment wall/floor, defined by radius, depth, and position offset.
- **Interior**: The usable volume inside a box, computed from outer dimensions minus wall/floor/lid thicknesses. Bounds all compartment and sub-box placement.
- **Project**: The top-level game insert description. A collection of multiple related boxes (e.g., an outer game box plus its nested sub-boxes) that orchestrates nesting layout and generates all pieces together. The public API surface; internally maps to BoxKit during export.
- **Spacer Box**: A hollow tray auto-generated to fill a gap in the nested layout. Has the same wall/floor construction as regular boxes but no compartments or lid. Minimum dimensions: 15mm width, 15mm length; may be shorter than 5mm in height.
- **3MF Export**: The output of a box or BoxKit -- a set of 3MF files written to disk, each containing embedded geometry with per-object material/color assignments (multi-color) or a single material (single-color). File naming follows `<label>_body.3mf` / `<label>_lid.3mf` conventions with `_single` suffix for single-color variants. Content-based caching via Hausdorff distance comparison prevents unnecessary file rewrites.
- **Layout PDF**: A packing guide generated alongside 3MF exports. Shows the game box interior from a 3D angle view. Includes layered exploded breakdowns: each row of boxes is rendered as a separate step where the top layer is displaced vertically to reveal boxes underneath, with arrows connecting displaced boxes back to their original positions. Boxes are labeled at their packed positions and numbered in packing order. Regenerated only when layout or library version changes.
- **Standalone Box**: A box generated and exported independently, with no enclosing game box, no nesting layout, and no packing phase. Built from a single `BoxSpec` and exported directly as body (+ lid if applicable).
- **Stackable Box**: A no-lid box with an interlocking rim. Two stacking modes: inside-fit (a recess on the top rim mates with the box above) and outside-fit (a ridge around the outside mates with the box below). Includes a configurable stackable thickness and fit offset for reliable interlocking.
- **Magnet Slot**: A cavity in a box side wall for an embedded magnet. Two types: round (cylindrical, configurable diameter and depth) and rectangular (box-shaped, configurable width, length, depth). Slots are placed on opposing sides so adjacent stacked boxes attract. Configurable count, size, and position per box.
- **Hex Grid**: A rectangular compartment region filled with a `rows × cols` array of hexagonal tile cutouts. Parameters: `tile_width` (apothem-to-apothem width), `spacing` (gap between cells), `rows`, `cols`, and `height`. The hex circumradius is derived as `tile_width / 2 / cos(30°)`.
- **Hex Cell**: A single hexagonal cutout within a Hex Grid, sized to hold one hex tile. Optional features: a central raised pillar (`push_block_height`) and a floor finger hole (`finger_hole_diameter`). The pillar and finger hole are mutually exclusive in the center — enabling both offsets the finger hole to the cell edge.

## Success Criteria

### Measurable Outcomes

- **SC-000**: Every shipped example builds and exports **without setting a single geometric override** — no radius, clearance, cutout size or fit parameter. What the examples set is what the game needs (sizes, contents, labels, colours). Any override an example is forced to add is a defect in a default, and the fix goes in the default (FR-000, FR-000a).
- **SC-000a**: Adding a box to a project takes a type, a size and its contents, and produces a printable body and lid. No parameter has to be set for the result to be usable.
- **SC-001**: A user can generate a complete box (body + lid + compartments) in under 10 lines of builder API code.
- **SC-001a**: A card box is described by its cards — how many, how big — and nothing else: the well's footprint, its depth and the box's height all follow. No example computes a height from the floor and lid thicknesses, or a well's depth by subtracting them back off.
- **SC-001b**: A value shared by every box in a project is written once. No example repeats a wall thickness, an `expandable` or a `no_rotate` per box, and no example repeats a lid style that differs only in its text.
- **SC-001c**: An example's entry point is one call. The preview-or-export branch appears once in the library, not in each example.
- **SC-002**: Automatic compartment layout (supporting 90-degree rotations of compartments) completes for 20 compartments in under 1 second.
- **SC-003**: All box lid types (sliding, cap, hinged, filament-hinge) produce geometry that mates correctly -- the lid and body can be assembled without modification.
- **SC-004**: 100% of invalid compartment configurations (overflow, excessive depth) are rejected at specification time with a descriptive error rather than producing broken geometry.
- **SC-005**: A nested box layout with 5 sub-boxes in a parent box produces valid, non-overlapping placements where the parent box can close with its lid on.
- **SC-006**: Finger cutouts on all four sides of a compartment can be specified and correctly carved without self-intersection.
- **SC-007**: Non-rectangular (polygon-path) boxes correctly clip all compartments and sub-boxes to the interior outline.
- **SC-008**: An auto-size layout with 6 sub-boxes (each with minimum dimensions) arranged into 2 rows completes in under 2 seconds and produces rows where every box in a row shares the same length.
- **SC-009**: After auto-sizing, any gap larger than 10mm between the expanded boxes and outer box walls is filled with a hollow spacer tray.
- **SC-010**: 100% of gap-fill scenarios with a gap under the 10mm threshold result in zero spacer trays -- the gap is absorbed by adjacent boxes.
- **SC-010a**: A layout whose leftover space forms N disjoint rectangular voids produces exactly N spacers, no matter how many boxes surround them. Specifically: the Emberleaf layout, whose 21 boxes leave three voids, produces exactly three spacers matching the original insert's `SpacerPlayer`, `SpacerSide` and `SpacerFront`.
- **SC-010b**: Merging is idempotent and order-independent — running the merge pass twice changes nothing, and shuffling the order of the boxes in a project yields the same spacer set.
- **SC-010c**: A single box in the corner of an otherwise empty layer leaves one L-shaped spacer with a six-point footprint, not two rectangular trays; a U-shaped leftover produces one eight-point spacer. Two leftover regions at different heights stay as two spacers.
- **SC-011**: Exporting a BoxKit with 3 sub-boxes and 2 spacer trays produces the correct number of 3MF files: (1 outer + 3 sub-boxes) x 2 (body + lid) x 2 (multi + single) + 2 spacers x 2 = 20 files total.
- **SC-012**: Re-exporting a project with zero changes writes **zero** files, however complex its geometry — including the SVG-silhouette and element-pack boxes whose meshes a boolean solver may retriangulate differently between runs. Measured on the Emberleaf insert: 79 files written on the first export, 0 on the second and 0 on the third.
- **SC-013**: Changing one sub-box in a BoxKit and re-exporting rewrites only the affected files (that sub-box's body + lid 3MFs, multi and single color = 4 files) while all other files are skipped.
- **SC-013a**: The same project exported at a different curve precision rewrites, since that is different geometry.
- **SC-013b**: A re-export with nothing changed **builds no geometry at all** — not merely writes no files. Measured on Irish Gauge at print precision: 35.9s for the first export, 0.1s for the second.
- **SC-013c**: Changing one box rebuilds that box and no other. Changing a lid's label rebuilds the lid and not the body; moving a box rebuilds neither; editing an SVG silhouette rebuilds every box that uses it and no other.
- **SC-013d**: Exporting one named box leaves every other file on disk untouched — same bytes, same timestamps.
- **SC-013e**: Previewing one named box builds only that box.
- **SC-014**: A lid with label text "Cards" auto-sized on a 100x70mm lid produces text with height ≥ 4mm and fills the lid area minus a 5mm border margin.
- **SC-015**: A lid with label text "A" on a 30x20mm lid produces zero label geometry (skipped because text height < 4mm) and no 3MF color assignments for the label.
- **SC-016**: A framed label exported as multi-color 3MF produces exactly the expected material assignments: body color for the lid slab **and for the plate the label sits on**, text color for the lettering, frame top color for the striped grid.
- **SC-016a**: A lid's top face is **flat**: a labelled lid measures the same height as the same lid unlabelled, and nothing of the label stands above the face. The label is a recess filled flush, not an embossing (FR-022a).
- **SC-016b**: The recess is cut only where a different colour goes. In framed mode the plate between the lettering and the striped grid is uncut, so it is the box's own material with no insert of its own.
- **SC-016c**: With no accent colours set, the lettering is black and the striped grid light grey — a legible lid without setting anything (FR-000a).
- **SC-016d**: A single-colour export still engraves its text, since it has no second material to inlay.
- **SC-016e**: A lid's pattern reaches its border exactly — measured on the cut lid, the nearest hole is the border away from the edge on all four sides, not more — and the holes at the edge are partial.
- **SC-016f**: A hexagonal pattern's holes are all exactly one pitch from their neighbours in every direction, so the web is the same all round.
- **SC-016g**: A label, including a diagonal one, stays inside the lid's border **plus its own 2mm inset** — 10mm from the lid's edge, against the pattern's 8mm.
- **SC-050a**: Every sliding-lid type — sliding, sliding-catch and card-library — carries a fingernail dish at its exit end, centred across the lid, and none of the other types does.
- **SC-050b**: The bowl is a spherical cap: a section along the slide is an arc, deepest at the wall and shallowing to nothing at the rim, and it removes material without reaching the lid's underside — the plate measures its full thickness everywhere outside the dish and at least half of it beneath.
- **SC-050e**: The dish is **half** a cap, not a whole one. Measured along the slide axis from its centre: inboard the lid is cut away, outboard it measures full thickness all the way to the lid's edge. The wall between them is as deep as the dish, to within a tenth.
- **SC-050c**: The dish's wall stands on the lid's border line, with the plain band at the edge outside it and the bowl inside it.
- **SC-050d**: A lid pattern leaves 1mm of solid lid all round the dish: no hole opens onto its rim.
- **SC-016i**: With no margin set, a frameless label's holes stop at the glyphs: no solid halo surrounds the lettering, and no hole undercuts a stroke.
- **SC-016j**: Each coloured part of a decorated lid reports the colour it prints in, and a preview draws the lid, the lettering and the striped grid in three different colours — never all three in the lid's.
- **SC-016h**: A lid's pattern is symmetric edge to edge: the material removed within a millimetre of the border measures the same on the left as on the right, and the same at the top as at the bottom, at any lid proportion.
- **SC-017**: A 4-box Project exported produces `layout.pdf` in the game output directory showing all 4 boxes at their packed positions with correct labels and dimensions, split by layers across one or more pages.
- **SC-018**: Re-exporting an unchanged Project skips `layout.pdf` regeneration (same as 3MF files — zero writes if layout hash matches).
- **SC-019**: The generated `layout.pdf` MUST be a valid PDF file that renders correctly in any PDF viewer, broken down layer-by-layer across multiple pages (e.g. Base Layer, Middle Layer, Top Layer). It MUST NOT use flat top-down or side views; instead, it MUST draw the game box and packed sub-boxes in a 3D oblique or isometric projection (viewed from above and to the side). On each page, the boxes belonging to the active layer MUST be drawn in full color, while boxes in the layers underneath MUST be drawn in light gray to show background context. The text labels on the boxes in the layout PDF MUST be visible, larger, and highly readable. If a label is hidden/blocked because another box sits directly on top of it, the label text MUST be shifted to the side. The text label MUST only display the label of the box (and not display the size/dimensions of the box).
- **SC-020**: A standalone box (no game box) exports exactly its body and lid 3MF files, with no packing phase, no layout PDF, and no spacer generation.
- **SC-021**: A stackable no-lid box exports an interlocking rim so that stacking three boxes of the same type nests them securely; the top box's rim mates with the box below without sliding more than the configured fit offset.
- **SC-022**: A box with round magnet slots produces cylindrical cavities of the configured diameter and depth on opposing sides, and a box with rectangular magnet slots produces rectangular cavities of the configured width/length/depth on opposing sides.
- **SC-023**: A hex (6-sided) box with 4 internal divisions produces 4 equal compartments clipped to the hexagonal interior, matching the stackable hexes reference example.
- **SC-024**: An edge scoop's profile shows both radii: r1 leaves the top face horizontally, r2 meets the floor horizontally, and setting either to 0 measurably changes the cut while leaving the other intact.
- **SC-025**: A scoop cut through a wall of any thickness spans that wall exactly — clear of both faces by no more than the boolean fudge — so both face fillets land on the faces rather than in the air beyond the box.
- **SC-026**: A scoop never opens the box's base: its lowest point stays inside the floor thickness, dipping below the well floor only by the configured clearance (default 0.2mm) so no face is left coplanar with the floor.
- **SC-027**: Every box body measures exactly its declared width, length and height after rounding — the fillets remove corner material only, leaving the flat faces (and therefore the packing envelope) untouched.
- **SC-028**: A rounded box's lid does not intersect its body: rounding adds no material to a mating surface, verified as 0mm³ of body/lid intersection across all eleven lidded types, including the partial lids whose grip is rounded on both halves.
- **SC-029**: An edge selector for "the vertical corners" resolves to exactly four edges, and a box rounded with it has all four corners rounded.
- **SC-030**: A fillet renders as a curve, not a chamfer: an edge rounding uses at least 32 facets per full circle regardless of how small its radius is, so the face it blends into is pulled in by less than 0.01mm.
- **SC-031**: A cut's face fillet removes material only where the face meets the cut, leaving the surrounding face otherwise untouched — no groove is cut around the opening, and the fillet traces the cut's outline rather than ramping across its opening.
- **SC-032**: A well is square unless declared a piece tray; one that is declared a tray, of depth D, has **both** corner and floor radii of D x 2/3 (capped by its footprint), while an SVG silhouette well and an element pack stay at 0 even when declared.
- **SC-033**: `export()` with no precision argument builds at 256 facets per circle; `show()` with no precision argument builds with no fixed facet count.
- **SC-033a**: A box previewed and the same box exported are built from an **identical** description — field for field, including its rounding, its `rim_free`, its `inner_rounding` and its per-side wall tops. Asserted by building one box through each path and comparing the two descriptions, not by inspecting the code.
- **SC-033b**: Every pattern in the catalog draws a distinct shape: no two members share a fill, and a member with no fill raises rather than substituting one.
- **SC-033g**: No part of the library answers a failure with silence. A missing geometry backend raises from the exporter, from lid decoration, from compartment labels and from a hex grid, and the message names the package, what it was for, and how to install it. A piece with no geometry raises rather than writing a 0-byte file. A spacer that cannot be built, a colour that cannot be applied, and a layout sheet that cannot be drawn all raise rather than being dropped. A cache that cannot be read or written is still a miss, not an error.
- **SC-033c**: A LEAF lid is cut with leaves, not with another member's shape: the material it removes differs from the same lid patterned HEX at the same pitch, each hole is twice as long as it is wide and does not fit in a square, and each carries a midrib.
- **SC-033d**: The leaves tessellate. No leaf touches its neighbour along the row or in the rows either side; the web measured between rows equals the web measured along a row, to within a thousandth; the row step is less than a leaf's width plus the web, so the rows demonstrably interleave; and the pattern opens more than a third of the lid's area.
- **SC-033i**: A small lid's Voronoi pitch is floored rather than derived, so it does not come out as pinholes: a lid whose eighth-of-the-shorter-side would fall below the floor still opens more than 45% of its area. A large lid keeps deriving its own. An explicitly requested pitch below the floor is honoured.
- **SC-033h**: A VORONOI lid is cut with cells, not circles: the pattern opens more than 70% of the area it fills — more than a disc inscribed in each cell could — the cells are irregular rather than lined up in columns, the seeds overhang the area so the cells at its edge are bounded by real neighbours, and two builds of the same lid produce identical geometry.
- **SC-033e**: The LEAF_TESSELLATION tile really tiles: its outline has seven points, its tip edges are equal and opposite to its base edges, its one long base edge is matched by the two short notch edges together, and its area equals exactly one cell of the lattice it is laid on. At the same pitch it opens more of the lid than LEAF does, because the leftover is only the web.
- **SC-033f**: LEAF_VEINS removes **less** material than LEAF_TESSELLATION at the same pitch — the veins are material kept, not cut — and every vein runs forward from a point on the midrib to a point on the margin, none of them from the base.
- **SC-033c**: A keyword a box type does not have raises, naming the keyword and the type. No builder field exists that the geometry does not read.
- **SC-033d**: N compartments each asking for `1/N` of the width fit, for every N from 1 to 4, on a box whose interior is exactly divisible — the layout's own spacing is inside the ratio, not on top of it.
- **SC-034**: The full test suite completes in about a minute at draft precision, against over five at print precision, and writes no printable output.
- **SC-035**: Every example project builds its complete geometry through the preview path in about ten seconds, writing no files.
- **SC-036**: A sliding box's lid channel reaches the open end: the lid can be translated out along the slide axis without intersecting the body at any point along the way, and the stop wall at the far end remains.
- **SC-037**: A finger hole cut with no arguments beyond its side is a usable scoop on every walled box type — its top rolls over, its height follows its radius, and its top edge sits at the interior's top rather than at the rim.
- **SC-038**: A compartment finger scoop reaches the box's top face, and its widest point is at that face — there is no step where the wall resumes above the cut.
- **SC-039**: A compartment scoop with no side given lands in the shorter wall; a sliding lid on a box longer than it is wide leaves through a face of the box's width.
- **SC-040**: On a sliding box, a finger scoop lands in the wall the lid exits by, whatever the compartment's proportions, and removes no material from either groove.
- **SC-041**: A sliding lid's rounding touches only its exit end: the two groove edges and the stop end measure square, and the radius never exceeds half the lid's thickness.
- **SC-042**: A scoop on a sliding box's exit wall tops out at that wall's height (a lid thickness below the box's top), while the same scoop on a lidless box tops out at the box's top — the per-side model, observed.
- **SC-043**: A silhouette slot's pull-out is half the piece's depth by default, is rounded on every edge, and can be declined per slot.
- **SC-044**: A scoop on a shallow wall has the same mouth width as the same scoop on a deep one; only the roll's rise differs.
- **SC-045**: A sliding lid's dovetail measures the **box interior across its top face** (the width minus twice the wall thickness) and **half the wall width across its bottom face** on both edges — wider at the floor than the opening, so it is trapped in the groove and cannot be lifted out, while half the wall remains behind the groove for support — the flanks are straight and angled, the grooves are the mirror image, and the lid's leading end carries a chamfer while its stop end stays square.
- **SC-046**: A compartment in a hinged box is clipped clear of the hinge: no well material lies within the barrel's reach of the hinge wall.
- **SC-047**: A slipover sleeve has material removed at two diagonally opposite corners and nowhere else, and the notches leave the sleeve's declared footprint unchanged.
- **SC-048**: A sliding box's channel is dovetailed into its stop wall exactly like the two sides — sliced at the channel floor and at the channel opening, its closed end differs by half a wall — and the lid's leading end reaches into that seat. It is a seat and not a wedge, measured by the travel: sliding the closed lid out along its axis, at every point the lid and body share **zero** volume, while lifting the closed lid straight up drives it into the body within half a millimetre. The lid-to-groove clearance is configurable, defaulting to 0.1mm per side.
- **SC-049**: A sliding box's catch is a bump and a dimple, and both sit within a wall thickness plus two bump radii of the **outlet** face — nearer the mouth than the stop wall, and on the walls the slide axis actually puts the grooves in. The dimple's diameter exceeds the bump's, so they click rather than jam. A plain sliding box has neither; a sliding-catch box has both, and asking a plain sliding box for a catch adds them.
- **SC-050**: A sliding lid's vertical corners are rounded and both horizontal edges of its leading end are chamfered — each measured against the same lid with that feature switched off, since the chamfers land close to the seat's own taper and a within-one-lid comparison cannot tell a chamfer from the slope it sits on. The lead chamfer is a quarter of the lid thickness by default.
- **SC-051**: A cap box's body has material removed at **all four** corners below the skirt and at none of its four side midpoints; each cutout runs between 10mm and a sixth of its side; a 2mm foot of body survives below it; and the two profile radii total at least 4mm.
- **SC-052**: A cap box builds at exactly `lid + 3 + 4 + 2` mm tall and raises a tenth of a millimetre below it, with a message naming the height, the minimum, its terms and the slipover alternative. A tall cap box's skirt is unchanged by the cap that makes this exact.
- **SC-053**: A no-lid box carries a finger hole in each of its two longer walls, each with radius `min(20, min(length, width) / 4, height - floor_thickness + 1)`, height `min(finger_hole_size, height - 2 + 1)`, and a 3mm mouth rounding.
- **SC-054**: A wall scoop's floor fillet tracks the **throat radius** and its top roll tracks the **mouth flare**: changing the flare alone leaves the floor fillet unchanged, and changing the throat radius alone changes it.
- **SC-055**: A lidless box's inner top edge is rounded by the same radius as its outer one; a lidded box's is not.
- **SC-056**: A hinged box's body and lid together measure exactly the declared width, length **and** height — nothing protrudes in any direction — and the two halves still share no volume.
- **SC-057**: A cap box's corner indent measures the same depth as the lid's offset — probing inward from the outer face at mid-cut height, material begins at exactly that offset.

- **SC-059**: A compartment scoop's face fillet reaches its flat bottom and tapers out there: at the base of the cut the wall's face rolls into it on both faces, no cross-section of bare wall is left, and the cut still dips no more than 0.2mm below the well floor.

- **SC-062**: A 14mm-wide fingertip prism, stood on the flat bottom of any default finger cut in the library, is entirely inside the removed material — the cut admits the finger it is sized for, whichever formula produced it.
- **SC-063**: Two finger cuts placed so they overlap — or one placed over a magnet pocket or a lid track — are reported by name and position at specification time rather than emitted as a single merged cut.
- **SC-065**: Every automatic finger hole leaves at least 5mm of tray wall below it, and a tray with no room for that strip plus a 2mm cut has no automatic holes at all.
- **SC-077**: Every sliding-lid type — sliding, sliding-catch and card-library — has its top outer edge rounded by a quarter of the wall, and a lidded type that is not sliding still measures square there.
- **SC-076**: A through-floor cut takes no more of the box's base than its bore and its wall slot do — measured inside the well and beyond the bore's own circle, it removes no more than a build with no inner overshoot at all.
- **SC-075**: A through-floor cut holds one section across the wall — sampled at its inner face, a quarter in, the middle and a fillet inside its outer face, the width varies by less than 0.2mm — and is wider only at the outward face itself.

- **SC-073**: A compartment asking for a finger cut gets a hole **through the box's base** by default — a probe under the box, beneath the cut, is open to the outside — and asking for a scoop instead leaves the base solid there.
- **SC-072**: A 6.5mm-deep card well gets a **wall notch** — a dip breaking its wall's top edge over most of the cut's width — and a 4mm tray still gets the floor bore.
- **SC-071**: **No cut's outline ever runs backwards or downwards** on its way from the base to the rim, at any combination of width, depth and roll — including the shallow ones where the roll is clamped. ## Assumptions

- The target fabrication method is FDM 3D printing with a minimum nozzle diameter of 0.4mm, so wall thicknesses below 1.2mm are not expected.
- The primary geometry engine is PythonSCAD (pybosl2), generating CSG solids consumed by OpenSCAD.
- Users have basic familiarity with 3D modeling concepts -- dimensions in millimetres, the coordinate frame (X=width, Y=length, Z=height), and the concept of subtracting cavities from a solid.
- Compartments are open-topped wells carved into the box floor; lids are not provided per-compartment (the box lid covers all).
- Boxes are right-rectangular by default; polygonal outlines are a secondary option.
- Labels on lids are single-line text with configurable font, size, and depth; multi-line labels are out of scope.
- The automatic layout algorithm uses a shelf-based 2D bin-packing strategy, not 3D packing (all compartments share the same floor level but may have different depths).
- Finger cutout dimensions default to adult fingertip sizing — a 14mm throat radius — but are configurable. A cut is swept **exactly through the wall it passes** (SC-025); there is no separate cut-depth dimension, and the wall's own thickness is what sets it.
- Smoothness comes from **tangency at both ends of each arc**: r1 tangent to the top face and to the throat, r2 tangent to the throat and to the floor. Two radii state that more directly than any curve fitted between them, and each is a number a designer can set.
- A rounded edge is a faceted approximation, so it pulls the face it blends into inwards by the sagitta, `r x (1 - cos(180 deg / fn))`. Declared dimensions are therefore exact to within that tolerance rather than to the last decimal — at the 48-facet floor it is ~0.002mm, well inside the 0.1mm dimensional precision the library promises.
- Nested sub-box packing is 2.5D (footprint + height): sub-boxes are placed upright and packed by footprint, then checked for height fit within the outer box interior height.
- Auto-sizing distributes space using a fill-to-fit row strategy: boxes in the same row share a common length (the longest in that row), and row widths are variable -- determined by the widest box in each row, not forced equal across rows.
- The auto-fill gap threshold defaults to 10mm: gaps smaller than this are absorbed by adjacent expandable boxes instead of generating spacer trays.
- Spacer boxes are hollow trays (walls + floor, no compartments, no lid) with a minimum footprint of 15mm x 15mm; they may be shorter than 5mm in height.
- 3MF files are written to a user-specified output directory. File naming follows `<label>_body.3mf` / `<label>_lid.3mf` for multi-color, with `_single` suffix for single-color variants. Box types without lids (no-lid, path-box) only produce body files.
- The Hausdorff distance tolerance for content-based caching defaults to 0.001mm to absorb floating-point jitter while detecting real geometric changes.
- Label text auto-sizes to fill the available lid area minus a configurable border margin (default 5mm per side). The minimum text height threshold defaults to 4mm -- labels that cannot render at this size are skipped.
- Lid decoration accent colors default to distinct values from the body color: label text defaults to white, frame top layer defaults to a contrasting hue, and pattern top layer defaults to a third contrasting hue.
- Through-hole patterns stop at the label boundary -- the label text and frame take visual precedence over decorative holes.
- Diagonal text orientation follows the lid's natural corner-to-corner angle (not forced to 45°) for non-square lids.
- Framed labels include diagonal hatching lines behind the text at a spacing that allows the text to bridge without supports.
- Through-hole patterns clip at all lid boundaries — partial holes at lid edges are truncated (same as label intersection clipping).
- PDF packing guide renders boxes as solid shaded models from an isometric camera angle (30° above horizontal, 45° rotated) with semi-transparent walls to reveal hidden interior boxes.
- Performance baselines assume Apple Silicon or equivalent x86-64 hardware. Cached regeneration targets < 1s for compartment layout and < 2s for auto-sizing. Uncached first-run packing may take 30s–5min depending on box count; no upper bound is guaranteed.
- `.layout_cache.json` is expected to remain < 1MB for typical projects (< 50 boxes).
- Missing pybosl2 or pymeshlab dependencies at import time produce a clear error message naming the missing package and minimum required version (pymeshlab ≥ 0.2.0).
- SC-003 (assemblability without modification) is verified via render tests checking mating geometry dimensions; physical print validation is deferred to the user.
- Borrowed tessellation files are assumed to be stable; if they are refactored, pattern fill functions under `pyboxbuilder/lid/pattern.py` must be updated accordingly.
- The original `.scad` examples encode their game-box layout in a `BoxLayout` module with explicit `translate`/`rotate` positions. When porting an example, the `BoxLayout` positions MUST be reproduced as manual `position=` values (with `no_rotate=True` and any 90° rotation baked into `size` by swapping width/length) — the layout is data, not a solver problem. The 3D auto-packer is a fallback for boxes without manual positions.
- **Boards go on the top of the box.** For layout and box generation, the game board (and any score pads / flat boards) is placed on TOP of the sub-boxes — it is the top layer of the insert, the first thing removed when opening the game box. `board_thickness` is therefore the reserved height at the TOP of the game box (`z = game_box_height - board_thickness .. game_box_height`), and the sub-boxes occupy `z = 0 .. game_box_height - board_thickness`. The board area MUST NOT be treated as a spacer gap.

### High-level Project Presets

To streamline insert definition and eliminate boilerplate code, the `Project` class exposes high-level presets:
- **`Project.card_box(...)`**: Automatically instantiates a `BoxBuilder` and populates it with a card deck compartment (`builder.cards(...)`), calculating sleeved footprint margins and card thickness automatically based on `SleeveType`.
- **`Project.token_tray(...)`**: Automatically instantiates a `BoxBuilder` and populates it with a grid of token compartments of relative ratios, each carrying a finger scoop on the specified `scoop_side` for easy piece retrieval.
- **`Project.hex_tile_box(...)`**: Instantiates a `BoxBuilder` configured with a compartment holding hexagonal tiles (`ElementShape.HEXAGON`) scaled by tile width.

### Architectural Modularization

The `project.py` module is split into a directory-based package `pyboxbuilder/project/` containing:
- `piece.py`: Lazy geometry piece representations (`Piece`, `ResolvedBox`, `Build`).
- `core.py`: Layout packing, export orchestration, and presets.
- `__init__.py`: Clean public API exposures.
